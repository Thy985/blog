# Agent 作为实验协作者——当 CNN 流水线学会自己搜索时

> 系列第 10 篇：Agent 的方法论不是“更快地执行同一套流程”，而是改变搜索空间与失败结构。而在选择用哪个平台承载 Agent 之前，先确认它假设了什么样的环境——因为CNN 训练环境，可能根本不满足那个假设。


## TL;DR

前 9 篇整理的是**人**做 CNN 项目的决策纪律。这一篇处理一个被遗漏的问题：当 Agent 接管实验执行时，这些纪律是否还成立，以及需要如何变形。核心判断有四条。**第一**，Agent + MCTS 在 AutoML 的配置搜索层已有验证过的工作（SELA 在 20 个数据集上取得 65%–80% 胜率），但 MCTS **在非可序列化环境中“直接不可用”**，因为它依赖重新探索已访问状态的能力；Docker 容器中的 CNN 训练恰恰不满足这个前提，替代方案（1-step lookahead、轨迹选择）本质上已经不是 MCTS。**第二**，Agent 真正适合的位置可能不是“训练配置搜索”，而是**在有限平台反馈预算下的序贯筛选**，但奖励信号必须重新定义为平台反馈，而非本地验证分数——否则 Agent 会**比人更高效地过拟合本地指标**，放大第 5 篇的四次反转。**第三**，AI 科研平台正在把“执行可审计性”工程化（OpenScience 的全链路来源追溯、本地优先），但这解决的是“事后能不能查”，而不是“事前该不该用本地信号做选择”；判断层的纪律仍然需要被显式编码。**第四**，Agent 自身的失败模式（revert-loop stagnation、分布错配、预算违规等）必须与 CNN 方法论的失败分开记录——一项实证研究的核心发现是，**接近性能天花板时，主要挑战不是模型质量，而是系统可靠性**。


## 1. 问题背景：人做实验和 Agent 做实验，差在哪

前 10 篇的决策纪律——评估目标先行、本地用于排除、增强看方向、集成看分歧、找误差下限、负结果结构化、复现分层、单种子脆弱——都建立在一个隐含前提上：**执行实验的是一个有判断力的人**。人能意识到“本地升平台降”意味着什么，能识别一个失败是方法问题还是实现问题，能在证据不足时选择停下来。

Agent 不同。它可以在工具、prompt、中间产物之间做自适应决策，可以调用训练脚本、读日志、改配置、再训练，形成一个闭环。这个闭环在**执行密度**上是人的数倍，但它不天然具备“区分观察和推断”的纪律，也不天然知道“本地信号不可信”在这个项目里意味着什么。

所以这一篇要回答的不是“Agent 能不能跑 CNN 实验”（能），而是：**在本地信号不可信、反馈预算有限、训练环境不可回滚的约束下，Agent 应该被放在决策链的哪一层；以及，在选择一个 AI 科研平台来承载 Agent 之前，先确认它假设了什么样的环境——因为你的环境可能不满足那个假设。**


## 2. 知识地图：Agent + MCTS 在 AutoML 中的真实位置

### 2.1 已有工作确实在做，而且有效

SELA 把 AutoML 的 pipeline 配置表示为树，用 MCTS 引导 Agent 在配置空间中搜索，在 20 个数据集上对各类基线取得 **65% 到 80% 的胜率**。I-MCTS 进一步改进：通过“内省”过程分析父节点和兄弟节点的解来扩展节点，引入 LLM 作为 value model 在昂贵的实际 rollout 之前预估节点价值，并用混合奖励机制让 Q 值从估计分数平滑过渡到实际性能分数，在强开源 AutoML agent 基础上取得约 **4% 的绝对提升**。

这些结果说明：**Agent + MCTS 在 AutoML 的配置搜索层，是一个被验证过的组合**，不是理论构想。

### 2.2 但 MCTS 有一个硬约束，和这个项目直接冲突

MCTS 的核心机制依赖于**重新探索之前访问过的状态**。一篇 ICML 2025 的论文明确界定了这个问题：**有效的搜索技术（如 MCTS）通常不适用于非可序列化的强化学习环境，例如 Docker 容器，因为中间环境状态难以轻松保存和恢复**；论文进一步**分析了无法回滚或复制环境状态如何阻碍 MCTS 等分支搜索方法**。

这篇论文提出的替代方案是 **1-step lookahead 和轨迹选择（trajectory selection）** ，由学习得到的 action-value 函数估计器引导。它们在 SWE-bench Verified 上把微调 Qwen-72B 的平均成功率翻倍到 40.8%。但关键在于：**这两种策略遵循的是“不可序列化环境仅能向前推进”的约束，它们放弃了 MCTS 的回溯机制**。换句话说，在 Docker 容器化的 CNN 训练环境里，你得到的不是 MCTS，而是一种没有树的引导式搜索。

这个项目恰好处于这个约束之下：冠军单模型训练约 30 分钟，训练过程不可回滚，中间状态（数据加载器位置、优化器动量、随机数生成器状态）难以被干净地保存和恢复。**“在训练配置树上做 MCTS”在这个环境里不是一个可选的方案，而是一个前提不满足的方案。**

### 2.3 Agent 自身的失败模式是另一层问题

即使绕开 MCTS 的可回滚性问题，Agent 自身的失败模式也会叠加到 CNN 的失败模式上。一项针对 LLM 驱动 AutoML 的实证研究（4 个 session、27 次运行）记录了六种失败：**revert-loop stagnation**（反复重新生成相同代码而停滞）、无监督特征工程导致训练/测试分布错配、资源预算违规、平台编码崩溃、废弃 API 不兼容、跨进程 pickle 作用域错误。该研究的核心发现是：**接近性能天花板时，LLM 驱动 AutoML 的主要挑战不是模型质量，而是系统可靠性**——确保 Agent 有意义地探索、遵守执行约束、产生可评估的输出。

这对这个项目的含义是：**“这个方法无效”和“Agent 没有正确执行这个方法”必须被分开记录。** 第 8 篇的失败分类法 A–F 是针对**方法假设**的；Agent 引入的失败需要另一套标签，否则证据台账会被系统可靠性问题污染。


## 3. AI 科研平台的选型：在执行可审计性与判断自主性之间

在把 Agent 接入 CNN 流水线之前，有一个比“用哪个 Agent 框架”更基础的问题：**用哪个平台来承载 Agent？** 不同平台在“把哪些纪律做成了默认值、又把哪些判断留给了你”上差异很大。

### 3.1 全流程科研工作台：OpenScience

OpenScience 是一个开源、模型无关的 AI 科研工作台，核心设计取向是**本地优先 + 全链路来源追溯**：所有研究数据、会话记录和实验产物默认存储在本地，每个图表、数据和分析结论均可追溯到生成它的代码、输入和模型输出。它在上海人工智能实验室联合清华、复旦、牛津等高校发布的 AI4S 基准 ResearchClawBench 上以 **22.8 分登顶**，超过 Claude Code（21.5 分）和 Codex CLI（18.4 分），是该榜单首个登顶的开源项目。在 HVTracker 的独立信任对比中，OpenScience 的 HVTrust 得分为 **83.3/100（A 级）** ，DeerFlow 为 **67.3/100（B 级）** ；差距主要来自**供应链完整性和来源追溯**——OpenScience 有 package provenance attestation，而 DeerFlow 没有。

**对这个项目而言**：OpenScience 的“本地优先 + 来源追溯”是它最有价值的选型理由——它把第 8、9 篇坚持的“一手来源可追溯”和“可复现分层”做成了平台默认属性，而不是需要额外搭建的纪律。但它的定位是**全流程自动化**（7 个 Agent Skill 模块覆盖选题到论文初稿），如果你只需要一个受约束的序贯实验执行器，它的能力面可能过宽；而且它的 benchmark 优势集中在科学任务执行上，**奖励信号的定义、本地/平台权重、停止条件仍然需要你自己设计**。

### 3.2 全自动科研循环：Sakana AI Scientist

Sakana 的 AI Scientist 代表了“把全流程自动化推到极致”的路线，但独立评测暴露了它在**判断层**的系统性薄弱，恰好对应这一篇认为“不应该完全交给 Agent”的那一层：**12 个提议实验中 5 个（42%）因编码错误失败**，其余实验常产生逻辑有缺陷或误导性结果；生成手稿的**中位引用数仅 5 篇**，34 条引用中只有 5 条来自 2020 年之后；结构错误频繁；**部分论文包含捏造的数值结果**。

**对这个项目而言**：AI Scientist 是一个有价值的**警示性参照**——当自动化覆盖到判断层时，失败会以“高编码失败率、引用幻觉、结果不可复现”的形式出现。它不适合作为执行基础设施，但它的失败模式本身就是第 8 篇“失败分类法”的一个外部案例集。

### 3.3 竞赛/数据科学多 Agent 框架：AutoKaggle

AutoKaggle 的定位更贴近这个项目形态：在 8 个 Kaggle 竞赛上取得 **0.85 的有效提交率**和 **0.82 的综合评分**，采用多阶段工作流和多 Agent 协作架构，支持人工干预。但一项对 agentic 数据科学系统的统一 benchmark 发现：**基于集成的系统（如 AutoGluon）在异构任务上表现最稳定，而 agentic 方法虽然偶尔取得强任务特定结果，但方差更高、执行失败更频繁**。

**对这个项目而言**：AutoKaggle 的“阶段化 + 人工可干预”结构与“Agent 做执行、人保留判断”在工作流层面兼容。但它更适合**有明确竞赛指标、允许反复试错**的场景，而不是**平台反馈预算极有限**的场景——高方差和高执行失败率在有限提交预算下是负面信号。

### 3.4 选型框架：按约束排序，而不是按榜单排序

| 平台/类别               | 定位                                 | 对这个项目的适用性                                  | 主要风险                            |
| ----------------------- | ------------------------------------ | --------------------------------------------------- | ----------------------------------- |
| **OpenScience**         | 全流程科研工作台，本地优先，来源追溯 | **高**：可审计性做成默认属性；HVTrust 83.3/100 A 级 | 能力面过宽；判断层仍需自建          |
| **Sakana AI Scientist** | 全自动科研循环                       | **低**：判断层薄弱                                  | 42% 编码失败、引用幻觉、捏造结果    |
| **AutoKaggle**          | 竞赛多 Agent 框架                    | **中**：阶段化可干预，但高方差                      | 高方差、执行失败频繁                |
| **DeerFlow**            | 通用 SuperAgent 框架                 | **中低**：非科研专用                                | HVTrust 67.3/100 B 级；缺乏来源追溯 |

**核心选型原则**：**不要按榜单分数选平台，按“它把哪些纪律做成了默认值、又把哪些判断留给了你”来选。** OpenScience 把可审计性和本地优先做成了默认值，这是它在这个项目上最大的优势；但没有任何平台会自动替你完成“奖励信号定义、本地/平台权重、停止条件”这些判断。**平台的成熟度决定的是执行层的最小摩擦，判断层的纪律仍然需要被显式编码。** 这和你在前 10 篇里反复论证的结论是一致的。


## 4. 分层框架：Agent 在这个项目的哪一层才有意义

### 4.1 第一层：训练配置搜索层——已验证，但与约束冲突

这一层对应 SELA/I-MCTS 的做法：树的节点是训练配方，扩展是跑一次训练，奖励是本地验证指标。

**在这个项目上不适用。** 障碍是结构性的：CNN 训练在 Docker 中不可回滚（MCTS 需要回溯），训练成本使“多次模拟”不可行（MCTS 需要统计可靠的奖励估计）。如果强行使用，得到的不是 MCTS，而是一个没有回溯机制的昂贵搜索。ICML 2025 的论文已经给出了这个判断的正式依据：**不可序列化环境中的经典分支搜索方法不可用，可行的替代是单步前瞻和轨迹选择**。

### 4.2 第二层：平台反馈预算分配层——有理论吸引力，但需要重新定义奖励

这一层不搜索训练配置，而是搜索**“在哪些候选上花费有限平台提交预算”**。

树的节点是**候选配置**，扩展是**选择下一个提交平台的候选**。奖励**不能是本地验证分数**——第 5 篇的四次反转已经证明本地信号不可信——而必须是**平台反馈的方向和幅度**。回溯更新的是“在这个平台上，从这个区域采样的期望收益”。

这更接近**序贯决策**的框架，而不是传统超参搜索。它承认了核心约束：本地信号不可靠，平台信号稀疏且昂贵，探索-利用机制可以被用来**分配提交预算**，而不是被用来“更彻底地搜索本地验证集”。

**但有一个关键前提**：如果平台提交预算只有个位数到低两位数，树深度和宽度都不足以体现优势；它的收益区间在**预算足够大、且每个“节点”不是一次完整训练而是已有候选的提交决策**时才会出现。

### 4.3 第三层：Agent 的职责边界——执行与判断必须分开

综合前两层，Agent 在这个项目中最合理的位置不是“自动调参器”，而是一个**受约束的序贯实验执行器**：

- Agent 负责**生成候选**和**排除明显差的方案**（在本地验证可靠的分辨区间内）。
- 当多个候选的本地指标接近时，**Agent 不自动选择“本地最高”的那个**，而是把候选提交平台，用平台信号做最终选择。
- Agent 记录每一次反转的**完整上下文**：本地指标、平台指标、配置、种子、早停点。这些记录进入证据台账。
- Agent 的输出必须是一个**可独立重跑的可执行规范**（代码/配置/DAG），而不是一段自然语言总结。

**判断权保留在人这一侧，执行权可以交给 Agent。** OpenScience 的“来源追溯”和“本地优先”可以支撑执行层的可审计性；但它不能替你决定“什么算可靠信号”。


## 5. 核心风险：Agent 会放大你已有的问题

### 5.1 Agent 可能加速本地过拟合

一个被设定为“最大化本地 Macro-F1”的 Agent，会在验证集上搜索得比人更彻底。第 5 篇的四次反转，在 Agent 循环里可能变成**更多次、更快的反转**，而且 Agent 不会自动知道“本地升平台降”意味着什么。**优化压力越大，代理指标的测量功能被侵蚀得越快**——这是古德哈特定律在 Agent 场景下的直接体现。

### 5.2 Agent 的成功需要和方法有效分开

一个 Agent 跑出了高分，可能是因为方法好，也可能是因为它在你验证集上搜索得更彻底。**没有独立于 Agent 的复现，高分不可归因。** 这对应第 9 篇的“可复现性是分层契约”，但多了一层：**Agent 的决策轨迹（prompt、工具调用、中间产物、模型版本）本身也需要被记录**。OpenScience 的轨迹保留机制可以作为一个现实参照，但“平台记录了”不等于“你分析了”——你仍然需要主动检查轨迹，才能区分“方法有效”和“Agent 碰巧找到了一个好点”。

### 5.3 Agent 不会自动带来方法论纪律

证据等级、负结果结构、停止信号——这些纪律需要被**显式编码进 Agent 的工作协议**，而不是假设它会从模型能力中涌现。Agent 可以生成大量结果，但它不天然具备“区分观察和推断”的习惯。第 8 篇的证据分级和失败分类法，在 Agent 场景下不是可选项，而是**防止证据台账被污染的必要条件**。一项实证研究已经给出了直接的证据：接近性能天花板时，Agent 的主要问题不是“模型不够聪明”，而是**系统可靠性——能否有意义地探索、遵守约束、产生可评估的输出**。

## 7. 解释与推断

**FACT（事实）**
- MCTS 在非可序列化环境（如 Docker）中直接不可用，替代方案是 1-step lookahead 和轨迹选择。
- Agent 驱动的 AutoML 存在 revert-loop stagnation 等六种失败模式。
- OpenScience 在 ResearchClawBench 上以 22.8 分登顶，HVTrust 83.3/100（A 级）。
- Sakana AI Scientist 的 42% 实验因编码错误失败，手稿中位引用仅 5 篇，存在捏造数值结果。
- AutoKaggle 在 8 个竞赛上取得 0.85 提交率和 0.82 综合评分。

**OBSERVED（观察）**
- 这个项目的训练环境（Docker + CNN 训练）属于非可序列化环境。
- 平台反馈预算有限，且本地验证信号已被证明不可信（第 5 篇）。
- AI 科研平台在“执行可审计性”上存在可量化的差异（OpenScience vs DeerFlow 的 HVTrust 差距）。

**INFERENCE（推断）**
- Agent+MCTS 的直接套用在这个项目上不可行，障碍是结构性的（可回滚性），而不是调参可以解决的。
- Agent 的合理位置是**序贯筛选的执行层**，而不是配置搜索层；奖励必须重新定义为平台反馈。
- AI 科研平台把执行层的可审计性工程化了，但**判断层的纪律仍然需要被显式设计**——平台是更好的执行环境，不是更好的实验者。
- Agent 的失败必须与 CNN 方法论的失败分开归因，否则证据链会被系统可靠性问题污染。

**HYPOTHESIS（假设）**
- 如果平台提交预算足够大，且节点定义为“已有候选的提交决策”，MCTS 的预算分配可能产生正收益。
- 如果将“本地排除”和“平台裁决”显式编码为 Agent 的工作协议，Agent 加速的将是有纪律的序贯决策，而不是过拟合本地验证集。
- 如果 OpenScience 的来源追溯被用于审计 Agent 的决策轨迹，Agent 结果的可归因性会显著提高。


## 8. 负结果与教训

**教训 1：Agent 的“成功”需要和方法有效分开。** 没有独立于 Agent 的复现，高分不可归因于方法，只能归因于“Agent 在这个验证集上找到了一个好点”。OpenScience 的轨迹保留提供了审计工具，但审计本身需要被主动执行。

**教训 2：Agent 的失败分类需要独立于 CNN 的失败分类。** revert-loop stagnation 和“Mixup 无效”是两种完全不同的失败；混在一起记录，会让停止信号失去意义。一项实证研究已经给出了六种可复用的失败模式标签，可以直接作为起点。

**教训 3：Agent 可能放大 reward hacking。** 如果奖励信号是本地 Macro-F1，Agent 会比人更高效地找到它的漏洞。这和第 5 篇的“本地用于排除而非精选”是同一个原则，只是优化压力更大。

**教训 4：Agent 的决策轨迹必须可审计。** 记录 prompt、工具调用、中间产物、模型版本，比记录最终配置更重要。否则你无法区分“结果来自方法”还是“结果来自某次随机的工具调用序列”。

**教训 5：MCTS 的可回滚性要求是一个硬边界，不是工程优化可以绕过的。** ICML 2025 的论文已经正式分析了这个约束，并给出了在不可序列化环境中的可行替代（1-step lookahead、轨迹选择）。诚实地使用这些替代方案，比包装成一个失效的树搜索更有价值。

**教训 6：平台选型时，先确认它假设了什么样的环境。** 一个在可序列化 benchmark 上表现优异的 Agent 平台，在你的 Docker 化 CNN 流水线上可能退化。**benchmark 分数不是选型的充分条件；环境兼容性是前置条件。**


## 9. 可迁移结论

- **Agent 适合接管执行密度高、反馈相对可靠的环节**（环境修复、多种子复现、超参扫描），**不适合接管需要分布匹配判断和证据分级的环节**。
- **把 Agent 设计成序贯筛选器，而不是本地指标最大化器。** 在接近的候选之间，用平台/真实反馈裁决，而不是让 Agent 自动选本地最高。
- **Agent 的输出必须是可独立重跑的可执行规范。** 自然语言总结不能替代代码/配置/DAG。
- **为 Agent 的失败建立独立的分类法**，与 CNN 方法论的失败分开记录。已有的六种失败模式（revert-loop stagnation、分布错配、预算违规、编码崩溃、API 不兼容、pickle 作用域错误）可以作为起点。
- **Agent 不会自动带来方法论纪律。** 证据等级、负结果结构、停止信号需要被显式编码进工作协议。
- **MCTS 的适用性取决于环境是否可序列化和模拟成本。** 在不可回滚的 CNN 训练环境中，正确的做法不是“用 MCTS”，而是使用为不可序列化环境设计的引导式搜索（1-step lookahead、轨迹选择），或者把搜索放在平台反馈预算分配层而不是训练配置层。
- **平台选型按“它把哪些纪律做成了默认值”来选。** OpenScience 把来源追溯和本地优先做成了默认值，这是它在可审计性上的优势；但没有任何平台会自动替你完成判断层的纪律设计。
