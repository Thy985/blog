# 项目全貌——任务、数据、约束与评估目标

> 系类第1篇：在选模型之前，先搞清楚在优化什么

### TL;DR

这是一个天气图像四分类任务：sunny / cloudy / rainy / snowy，训练数据约 4,990 张，类别不平衡比例约 1.75:1，隐藏测试集存在分布偏移，最终 Macro-F1 0.9137。但这一篇不写模型，也不写配方，只回答更本质的问题：**任务是什么、数据长什么样、约束有哪些、评估目标是什么**。

---

## 1.问题背景：为啥先讲评估目标

我一开始的直觉是：拿到数据，选个CNN，训练，调参，提交。

但项目做完回头看，真的决定成败的不是”选了ResNet18还是ResNet50",而是：

- 我用什么指标判断模型好坏？
- 这个指标和平台评估一致吗？
- 在平台评估是黑盒的情况下，如果保证验收？

这一篇的写作目标顺序是:**任务->数据->约束->评估目标。**

---

## 2.任务定义

### 2.1任务类型

这是一个**单标签图像四分类**任务：

| 类别 | 英文   | 含义       |
| :--- | :----- | :--------- |
| 晴   | sunny  | 晴朗天气   |
| 多云 | cloudy | 多云或阴天 |
| 雨   | rainy  | 降雨天气   |
| 雪   | snowy  | 降雪天气   |

输入是一张天气图像，输出是四个类别中的一个。

### 2.2任务难度

表面上看，四分类比ImageNet 1000类简单得多。但实际难度不在类别数，而在：

- **类别边界模糊**:cloudy和sunny在薄云、逆光、黄昏场景下非常接近。
- **类内差异大**:rainy可以是小雨、暴雨、夜间雨、车窗雨。
- **数据量小**：约4990张，对CNN来说偏小。
- **类别不平衡**：最大类与最小类比例约1.75:1
- **隐藏测试集分布偏移**:平台测试集与本地验证集分布不完全一致。

所以这不是“四分类很简单”的问题，而是“小样本+不平衡+分布偏移"的问题

### 2.评估指标

平台使用**Macro-F1**作为主要指标

为什么不是Accuracy?因为类别不平衡下，Accuracy会被多数类主导，模型稍微偏向多数类就能拿到好看的平均分。更关键的是，平台测试集的类别先验未知（见3.4的分布偏移），分布一旦偏移，最该盯的就是每一类各自的F1，而不是一个按样本量加权的平均数。Macro-F1对每个类别一视同仁，先计算每个类别的F1,再取平均，能暴露少数类问题。

这一点后面会展开讲，这里要记住：**在这个项目里，Accuracy不是决策依据，Macro-F1才是**

## 3.数据全貌

### 3.1数据规模

| 项目           | 数值        |
| :------------- | :---------- |
| 训练数据总量   | 约 4,990 张 |
| 类别数         | 4           |
| 类别不平衡比例 | 约 1.75:1   |
| 输入类型       | RGB 图像    |
| 标签类型       | 单标签      |

数据量小意味着：

- 从头训练的CNN容易过拟合
- 迁移学习几乎是默认选择
- 数据增强的收益和风险都被无限被放大
- 验证集划分的随机性会影响结论

### 3.2类别不平衡

1.75:1 的不平衡其实相当温和，单靠它不足以让 Accuracy 失真。这一点在后面的实验里被反复验证：真正让指标失真的不是不平衡本身，而是分布偏移。

项目尝试过：

- 加权采样
- 类别权重
- 推理锐化

结果都不理想，甚至负向。这部分后期会详细的写

---

### 3.4本地验证 vs 平台测试

这是整个项目最重要的数据特征：

- **本地验证集**：从训练数据中划分，可反复观察。
- **平台测试集**：隐藏，不可见，只能提交后得到反馈。
- **两者分布不完全一致**：存在分布偏移。

这导致了一个核心现象：**本地指标上升，平台指标下降。** 在项目里发生了四次，涉及分辨率、噪声、集成伙伴、混合权重四个维度。

----

## 4.约束条件

约束决定了方案的空间。这个项目的约束主要有五条

### 4.1数据量小

约4990张，对深度CNN来说偏小

影响：

- 优先迁移学习，而不是从头训练
- 需要正则化：Dropout、Weight Decay、BN
- 数据增强要谨慎，不是越多越好
- 交叉验证成本高，但必要

### 4.2类别不平衡

约 1.75:1（rainy 35% / snowy 20%）。

影响：

- 不能用 Accuracy 做主要指标。
- 需要看 Macro-F1 和混淆矩阵。
- 重采样和类别权重不一定有效，需要实验验证。

### 4.3分布偏移

本地验证与平台测试分布不一致。

影响：

- 本地验证不能完全信任。
- 需要平台反馈作为最终信号。
- 需要记录“本地升、平台降”的反转案例。
- 过拟合验证集的风险很高。

### 4.4 部署约束

这是最容易被忽略、但最硬的一条。

项目里 CLIP 变体因为**无法部署**被直接否决。不是效果不好，而是部署不了。

影响：

- 依赖检查必须前置。
- 模型选型不能只看指标，还要看推理成本、依赖、硬件。
- “能跑”比“跑得高”优先级更高。

## 5.评估目标

### 5.1 三层评估

项目里有三层评估：

| 层级       | 数据           | 可见性 | 用途           |
| :--------- | :------------- | :----- | :------------- |
| 训练集     | 训练数据       | 可见   | 拟合           |
| 本地验证集 | 从训练数据划分 | 可见   | 模型选择、调参 |
| 平台测试集 | 隐藏           | 不可见 | 最终评判       |

问题在于：**本地验证集和平台测试集不是同分布。**

### 5.2为什么Macro-F1是主要指标

Macro-F1的计算方式：

1.对每个类别分别计算Precision和Recall

2.对每个类别计算F1

3.对四个类别的F1取平均值

它和Accuracy的区别：

- Accuracy会被多数类主导
- Macro-F1对少数类更敏感
- 在类别不平衡时，Macro-F1更能反应真实性能

所以项目里所有关键决策都看Macro-F1,而不是Accurcay.

### 5.3平台差距

这里定义了一个分析维度：**平台差距**

它指的是：本地验证指标与平台测试指标之间的差异

这个差距不是噪声，而是信号。它告诉你：

- 本地验证集是否过拟合
- 增强策略是否匹配目标分布
- 集成是否真的带来泛化提升
- 某些技巧是否只在本地有效

项目里出现了四次反转：

| 维度     | 本地 | 平台 |
| -------- | ---- | ---- |
| 分辨率   | 升   | 降   |
| 噪声     | 升   | 降   |
| 集成伙伴 | 升   | 降   |
| 混合权重 | 升   | 降   |

这四次反转是第5篇的核心内容。

### 5.4评估目标决定模型选择

因为评估目标是Macro-F1+平台测试，所以：

- 不能只追求本地Accuracy.
- 不能盲目堆模型
- 不能只看单模型指标，还要看继集成后的平台表现
- 不能忽略部署目标

其实一开始就要**明确评估目标**

## 6.结果与证据

这一篇不展开实验细节，只给出项目最终结果作为锚点：

| 项目               | 结果                                |
| :----------------- | :---------------------------------- |
| 最终平台指标       | Macro-F1 0.9137                     |
| 冠军单模型训练时间 | 约 30 分钟（RTX 3060 级别）         |
| 误差下限           | 5 个异构模型在 8/499 样本上一致出错 |
| 主要错误区域       | cloudy ↔ sunny 边界模糊             |
| 最大单项提升       | 关闭合成噪声，平台 +0.017           |

证据来源：

- `results/`：主要产物 JSON / 日志
- `logs/`：原始训练日志
- `analysis/`：混淆矩阵、各类别指标、集成互补性、平台差距、误差分析
- `experiments/`：实验数据库、证据地图、证据台账
- `reports/`：最终报告、项目总结

## 7.负结果与教训

这一篇的负结果不是某个技巧，而是对评估目标的误判。

教训：

1.**不要先选模型，先确认评估目标。**

2.**不要用Accuracy判断不平衡数据**

3.**不要假设本地验证等于平台测试**

4.**不要忽略部署约束**

5.**不要只记录成功，负结果同样重要**

这些教训会在后续每一篇里反复出现

---

## 8.可迁移结论

如果你也在做小样本图像分类，这一篇结论可以直接迁移：

- 先定义评估指标，再选模型。
- 类别不平衡，优先选择Macro-F1
- 本地验证和真实测试不一致时，记录平台差距。
- 部署约束前置，避免训练完才发现跑不了。
- 数据量小的时候，迁移学习+正则化+谨慎增强时默认起点
- 一定要记录baseline，否则进行了负向学习也检查不出现
- 把负结果和反转案例写进实验记录
- 不要只追求F1分数上涨或者下降，一定要搞清楚背后为啥，这样才是科研，否则就是调参
