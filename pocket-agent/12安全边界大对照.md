# 安全边界大对照——四种信任模型针对同一威胁面

> 本系列出现过四种安全设计：星渡的策略类、DSHA 的白名单守门人、ZCode fork 的端点钉住、DSH 网关族的边界代理。上一轮它们都还是 README 口径；这一轮后三种已有源码背书——把它们摆上同一张解剖台，比较信任根、默认姿态与诚实度。

---

## 1. 统一威胁面

无论本机派还是远控派，一个"装了编程 agent 的手机"的威胁面由三个问题构成：

1. **谁能连上它**？（Web 端口暴露面：局域网/公网/桥）
2. **连上后能跑什么**？（agent 的工具执行 + 设备能力桥 + 插件）
3. **凭据放在哪、流到哪**？（API key、桥 token、会话 cookie、备份）

四种设计各自在不同位置设防——因为它们的攻击面权重不同。

## 2. 四种模型并排

| | 星渡 | DSHA | ZCode fork | DSH 网关族 |
|---|---|---|---|---|
| **形态** | 策略类群（ZipPathPolicy 8 行 / UrlPolicy / ScreenPrivacy…） | `DeviceShellPolicy` 类型化 Plan（READ/BLOCK/FILE/SENSITIVE_READ/DENY） | `RemoteControlUrlPolicy` sealed TrustDecision（Pinned/NeedsTrust/Invalid） | 边界代理（Host/Origin 双写）+ 39 具名方法白名单 |
| **信任根** | Android 沙箱 + 显式 URL 策略 | 设备授权通道 + 桥 token | 用户显式信任的端点（origin 钉住） | 配对/密码 + 网关白名单 |
| **默认姿态** | 截图保护默认开、不绕审批 | **未知命令不放行**（类注释："设备命令默认拒绝"） | 未知来源 → `NeedsTrust` 显式确认；http 单独 opt-in | 敏感接口默认关闭；匿名通道只读子集 |
| **越界处理** | 策略拦截，无放行弹窗 | `[POLICY_BLOCKED]` + `[EXIT=126]` | `Invalid` 类型转系统浏览器 | 失败熔断锁 IP；normalizeHost 解析失败即空串 |
| **诚实边界** | 验证状态表（22/26 过 + 4 项标注原因） | "不能推导的保证"列 + 已知缺口公开待修 | CSS 可靠性论证（连"不做"都给上游 file:line 理由） | "不提供全链路 TLS"逐项声明 |

## 3. 三个横切观察

### 3.1 类型化判定是收敛点

源码级对照后发现一个上一轮没看出的收敛：**四种模型不约而同把安全判定做成类型**——DSHA 的 `Plan(kind, argv, reason)`、ZCode fork 的 `sealed TrustDecision`、bluelightgit 的 `{method, privileged, readonly}` 元组。布尔值 `allowed: true/false` 被抛弃，因为安全决策的输出从来不是二元的：同一条命令可以是"允许/拒绝/需确认/结果未知"，**让类型系统承载处置的多样性**，调用方（executor/WebView host/gateway）才能对每类做出正确反应。这是"安全决策函数化"的通用形态，比"集中式安全类"还是"分布式策略对象"的架构之争重要得多。

### 3.2 fail-closed 的两种合法形态

- **设备命令**（DSHA）：未知 = 拒绝。因为命令空间无限、误执行代价不可逆（06 篇的 PID 复用防护说明连"合法命令"都要防竞态）；
- **URL 准入**（ZCode fork）：未知 = 需确认（`NeedsTrust` 是合法判定）。因为来源空间有限、用户可以读懂"是否信任此后端"、确认是可持久化的一次性决策。

**fail-closed 不等于凡事都拒**——判定逻辑的松紧跟"用户能否理解未知物"和"误判代价"走。StarJeke 的 Host 解析失败返回空串、bluelightgit 的 Origin 校验拒绝半解析结果，是同一个原则在解析层的形态：**宁可失败，不拿猜测去比较**。

### 3.3 实测教训比设计文档贵

10 篇 StyleJeke 的注释是最好的例证："只改 Host 不够——回环 Host + 外部 Origin **实测**同样是 403"、"cloudflared 会把 Host 改写成源站地址，两者永远不等"、"浏览器在沙箱上下文会发 `Origin: null`，那是合法请求"。这三条没有一条能从 DSH 文档推导出来——全是流量级别的撞坑。**安全设计的证据链优先级：实测日志 > 源码 > 文档**，本系列的证据分级（00 篇）正是照这个顺序排的。

## 4. 分工全景：谁在哪一层设防

```
通道层   Tailscale/SSH/frp ……  可达性（不管身份）         ← 09 篇
安全层   网关族：边界代理 + API 白名单 + 熔断             ← 10 篇
壳层     ZCode fork：端点钉住 + TrustDecision + token 卫生 ← 11 篇
系统层   DSHA：能力白名单 + 设备授权分级                  ← 06 篇
应用层   星渡：URL/路径策略 + 截图保护 + 审批不绕过          ← 03/04 篇
```

**没有一种模型覆盖全部层**——星渡不做公网网关，网关族不管设备能力，ZCode fork 不碰执行沙箱。生态的答案不是"一个更安全的方案"，而是**组合**：ZCode fork + Tailscale + bluelightgit 式网关，或 DSHA + 局域网 fail-closed token——15 篇决策表按场景给组合。

## 5. 项目锚点：安全取舍史

- **星渡**：ROADMAP 总原则把"不绕过审批、不加无约束 shell、不放宽 WebView 与 URL 策略"写进不变量区——**功能演进不得触碰**；
- **ZCode fork**：整个提交以"保留原有安全模型的前提下"为前提，六组改动逐条对应一个"补能力不开洞"（附件走 FileProvider 而非放开 allowFileAccess、分享只要 `clipboard-sanitized-write`、登录通道 origin 硬编码白名单）。

两个项目的共同点：**安全边界先于功能清单存在，且显式声明为不变量**——与"演进注记"（技术路线可以错、可以改）不矛盾：**路线可以变，边界不变量不随路线变**。

## 6. 边界与不足

四种模型均无第三方渗透测试；对照基于源码静态阅读与 README，未做动态验证；DSH 上游的栅栏实现本系列未直接读（以 StyleJeke 的 403 实测注释与网关适配代码为交叉证据）；网关族白名单默认集的宽严没有跨项目标准；威胁面随插件生态漂移——对照是 2026-10-24 快照。

## 7. 一句话总结

> 四种信任模型不是四个竞品，是同一条防线上的四段工事：网关守协议、壳守来源、系统守能力、应用守策略——它们的共同进化方向是把判定类型化、把未知分类处置、把"不做什么"写成带 file:line 的论证。
