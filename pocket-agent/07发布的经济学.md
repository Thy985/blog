# 发布的经济学——当应用太"危险"又太"大"

> 本机派应用有两个与生俱来的发布难题：它要在手机上执行任意工具链（触发应用商店的全部敏感神经），它带着几百 MB 的运行时（撞上渠道的体积红线）。星渡 ROADMAP 里那张渠道约束表，是这一章最好的教材。

---

## 1. 四个渠道，四套规则

星渡 ROADMAP（2026-10 调研结论）的原文表格：

| 渠道 | 约束 | 对本项目的影响 |
|---|---|---|
| GitHub Releases | 无体积限制 | **正式发布的主渠道**；正式签名后即为稳定版分发通道 |
| Google Play | 2026-08-31 起新应用/更新须 target API 36+（现有应用须 35+ 才可被发现） | targetSdk 28 依赖"应用数据目录可 exec"，API 29+ 被 W^X 禁止；**必须把二进制迁移到 nativeLibraryDir（jniLibs 打包）才可能升级** |
| IzzyOnDroid | 单 APK 惯例约 30 MB | 内置约 211 MiB `runtime.zip` 的全量包不可能；**只有"瘦包 + 首启下载运行时"方案才可能达标** |
| F-Droid 官方库 | 原则上禁止预编译二进制，须从源码构建 | 捆绑的 Termux 编译 Node 闭包无法过审；列为长期调研项（需源内构建 Node 或上游协作） |

结论同样是原文："主渠道为正式签名的 GitHub Releases；Play / IzzyOnDroid 在 0.3.0 阶段按瘦包可行性评估。"

## 2. 逐渠道拆解

**Google Play：targetSdk 与 W^X 的死锁。** Play 的合规要求（targetSdk 36）与产品架构（数据目录 exec）直接冲突——解法是 02 篇说的 jniLibs 迁移，但那意味着把 200MB+ 的运行时塞进 APK 原生库目录，Play 的 AAB 分发会按设备 ABI 裁剪（单 ABI 打包是必须的第一步）。迁移在星渡 ROADMAP 里排在 0.3.0，且明确"迁移后按同一清单重新验证"。

**IzzyOnDroid：30MB 惯例与瘦包。** 瘦包方案 = APK 只带壳和下载器，运行时首启从 GitHub Releases 下载。它引入一个新问题：**首启下载的信任链**——用户装的是签名的 A，跑的是后来下载的 B。解法是发布页与内置校验值对齐（SHA256SUMS + 包内校验），但"下载器信任"本身要写进安全模型。

**F-Droid：reproducible builds 的代价。** 禁预编译二进制的本意是可复现构建——对"自带一整套交叉编译 Node 闭包"的应用，等于要求把整条工具链搬进 F-Droid 的构建环境。星渡列为长期调研；DSHA 的做法对照：**干脆不进 F-Droid**，主打 GitHub Releases + 官网 + 应用内更新清单。

## 3. 签名与分发细节

三个项目的发布工程细节：

- **星渡**：当前是 Debug 开发预览（README 明确"不是正式签名的稳定发行版"），正式版的签名与版本号迁移在 ROADMAP 里；附件带 `SHA256SUMS.txt`；
- **DSHA**：v0.2.1-rc.2 是"E7E3 正式签名、非调试"，Standard/Low 双 APK（Low 内置 GeckoView 143），**新旧包名共存**（`dsh.android.client` vs `com.dsh.client`）并用备份导出/恢复迁移；发布说明连"覆盖更新前请先正常停止 DSH"的操作顺序都写明；
- **ZCode fork**（对照，11 篇详述）：release 签名只读环境变量（`ZCODE_KEYSTORE_PATH` 等），**仓库不落 keystore**；`-PzcodeAbi=<abi>` 单 ABI 打包——"MLKit 四套 .so 是包体大头"。

## 4. 通用的发布策略模式

把两个项目的选择抽象出来，本机派应用的发布策略空间是四个模式：

1. **全量包 + GitHub Releases**（星渡当前、DSHA 主线）：最简单，代价是用户自担侧载与更新；
2. **瘦包 + 首启下载**（星渡 0.3.0 候选）：解锁轻渠道，代价是下载信任链；
3. **双/多 APK 分设备**（DSHA Standard/Low）：兼容性兜底，代价是维护矩阵翻倍；
4. **源内构建**（F-Droid 路线）：可信度最高，代价是工程量最大——对个人项目通常是"长期调研"。

## 5. 演进注记

DSHA 的历史版本线（v1.1.10 → 双 APK 受管更新 → 0.1.x/0.2.x 重编号）显示它走完了一轮"发布架构迁移"（README 保留原文："完整直接升级矩阵尚未重新验证，原版说明保留在历史标签"）——**版本号重置 + 保留历史标签**是迁移期最诚实的版本学。星渡则处在迁移前夜（0.1.9 验证补全 → 0.2 架构迁移 → 0.3 渠道评估），路线图明确"先在现有架构上验证扎实并建好 CI，再做大架构迁移"。

## 6. 边界与不足

渠道规则随时会变（Play 的 targetSdk 门槛每年抬升）；"瘦包"方案在弱网/离线场景反而劣化（首启必须联网）；本文只覆盖 Android 三渠道 + GitHub，国内应用商店（对 agent 类应用基本关闭）未展开；签名信任链（谁签的名、用户为什么信）在侧载场景最终退化为"用户自己判断"——所有渠道策略都不能替代这一层。

## 7. 一句话总结

> 本机派应用发布难，难在它的本质：一个"能在你手机上执行任意工具链"的应用，天然是应用商店最警惕的对象——GitHub Releases + 正式签名是现实解，瘦包 + 下载信任链是进阶解，商店上架是长期工程。
