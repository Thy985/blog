# 星渡（上）——825MB 运行时进 APK

> 星渡的赌注是：不借任何发行版层，把 Bionic 版 Node.js、DSH 引擎、bash、ripgrep 直接装进 Android——825MB 运行时随 APK 分发，装完即用。这一章讲三件事：运行时从哪来（答案出乎意料）、386 行的 PTY 助手协议怎么设计、前台服务怎么管住引擎进程。

---

## 1. 运行时从哪来：借 Termux 的编译成果

`scripts/runtime/build-runtime.sh` 头注释给出了最重要的架构事实（我第一版写作误以为它是 NDK 重编，读后修正）：

> 选择 **Termux 官方 apt 仓库**而非上游官方 Node 二进制：官方 linux-arm64 是 glibc 链接，在 bionic 上无法直接运行；**Termux 的 node 为 bionic 交叉编译，开箱即用**。

脚本在 CI 的 x86_64 Linux 上配置 Termux 的 arm64 apt 源，把 Node 运行时闭包逐包收集、产出 `runtime.zip`。三个工程决策藏在注释里：

1. **站在 Termux 肩膀上**：不自己维护交叉编译工具链——Termux 社区已经解决了"Bionic 上编 Node"的全部脏活，星渡只做**依赖闭包收集**；
2. **许可证审计**：node（MIT）+ 依赖库（MIT/BSD/ISC/Zlib）允许再分发，**"刻意不打包任何 GPL 工具链组件"**——分发合规在构建脚本里就解决了；
3. **清单化**：`PKGS 清单基于 Termux 主仓库当前已知包名编写，仓库调整时按报错修正` + `dsh-runtime-resolved-lock.json` 锁定解析结果——上游仓库漂移可感知、可复现。

打包为约 211MiB 的 `runtime.zip`，首启解压约 825MB。运行时内容：Bionic Node.js 24.18.0、DSH 0.2.1-rc.2、Bash、ripgrep、CA 证书、文件锁辅助，以及两个自研 C 组件——`flock.c` 和下一节的主角。

## 2. dsh_pty_exec.c：386 行的 PTY 桥协议

这是星渡仓库里设计密度最高的文件。问题（头注释原文）：引擎的 Web 终端与持久 bash 工具都经 `@deepseek-ai/dsh-subprocess-local` 调 **node-pty** 申请伪终端，但 Android/Bionic 下 node-pty **没有预编译产物（runtime 里是显式抛错的空壳）**；App 侧已有的 libdshpty.so 只服务"拉起引擎主进程"且是 JNI——引擎是另一个进程，用不了。

解法：一个**独立可执行文件**，由引擎内的 node-pty 兼容层（`node_modules/node-pty/lib/index.js` 的 Android 实现）以普通子进程启动，职责四件：fork 挂 PTY 的 shell（`setsid + TIOCSCTTY`，真实 tty 语义）、PTY master ↔ stdio 双向搬字节、接收控制指令做 resize/信号投递、退出后回报退出码。

**协议设计**（文件头原文整理）：

```
通道约定（父进程 = node-pty 兼容层）：
  0 (stdin)  → 写入 PTY 的数据（用户按键）
  1 (stdout) → PTY 输出的数据（屏幕内容）
  2 (stderr) → 助手自身的诊断信息（不混入终端内容）
  3 (ctrl)   → 双向控制通道，行协议（ASCII，'\n' 结尾）：
                 引擎 → 助手： R <cols> <rows>   改窗口尺寸
                              K <SIGNAL>         向子进程组投递信号
                 助手 → 引擎： EXIT <code> <signal>
```

三处设计判断值得学：

1. **数据与控制分离**：字节流走 0/1，控制走独立 fd 3——终端数据里出现任何字节序列都不会被误解析为命令（对比"内嵌转义序列"方案的全套转义复杂度）；
2. **pidfile 而非管道**（`--dsh-pty-pidfile`）：fork 后立刻把子进程 pid 写进文件。为什么不用管道？——"引擎 spawn 后要**同步**读 terminal.pid（LocalTerminalHandle 构造时就取值），管道的非阻塞读会 EAGAIN，而普通文件短轮询读即可拿到——实现最简且无竞态"。一个文件 vs 一个异步管道协议，选了简单的那个并写明理由；
3. **stderr 明确隔离**：助手自己的诊断信息永远不混进终端内容流——终端复现对字节保真的执念（embodied-ai 系列 renderers 篇的"token 是账本"在终端世界的同款原则）。

## 3. 前台服务：DshService 的所有权设计

`DshService.java`（前台服务）是唯一拥有 DSH 进程的组件，类注释一句话定职责："**Owns one local DSH process. Credentials and launch URLs never leave this process via IPC.**"

实现细节：

- **FileLock 防双开**：启动前抢文件锁，两个引擎实例不可能并存；
- **代数计数器**（`processGeneration` / `generation`，volatile）：进程重启后旧异步回调凭代数作废——用世代号解决"进程换世代的竞态"；
- **日志环形缓冲 + 监听器**（`CopyOnWriteArraySet<Listener>`）：`LogParser` 从日志流抽引擎状态喂 UI；
- 单线程 executor 串行化所有进程操作——**一个服务一个进程一把锁**，简单但够用。

## 4. 补丁族：被 issue 编号钉住的工程

`scripts/runtime/patch-*.py` 每个文件头都写"为什么需要"并挂 issue：

- `patch-node-pty-android.py`："给 dsh 引擎补上 Android 的终端（PTY）支持——**issue #18 第二层**"（第一层就是上面的 C 助手）；
- `patch-ptc-runtime-android.py`："保留 LD_LIBRARY_PATH——**issue #29**。用户报障：重启引擎后 `run_code` 仍失败"；
- `patch-fs-local-android.py`："单一真源——本地改包与 CI collect-termux-runtime.sh 都调这一个脚本，避免两处漂移"；
- `patch-webview-polyfill.py`：为旧 WebView 注入现代 API polyfill（dsh 前端含 pdf.js/Excel 预览等 7MB 级插件）。

三条纪律：**补丁挂 issue**（存在性的证据链）、**单一真源**（杜绝两处漂移）、**补丁与上游解耦**（升级 DSH = 重放补丁族 + `verify-runtime.py` 校验）。

## 5. 边界与不足

825MB 首启解压对低存储设备不友好；**上游每新增一个原生依赖都要重走"查 Termux 仓库 → 收闭包 → 打补丁"流程**，补丁族随 DSH 生态增长而膨胀；node-pty 兼容层是 JS 层重实现，node-pty 上游 API 变化要同步跟；targetSdk 28 无法上架 Play（07 篇）；仪器测试 26 项中 4 项未过（环境/测试框架因素，README 如实标注）。

## 6. 一句话总结

> 本机派的第一种答案不是"自己重编 Linux"，而是**站在 Termux 编译成果的肩膀上做闭包收集**——真正的自研 concentrates 在缝隙处：一个 386 行的 PTY 桥协议和一族被 issue 钉住的补丁。
