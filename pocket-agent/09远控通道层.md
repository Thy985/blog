# 远控通道层——SSH 反向、Cloudflare、frp 与 CGNAT 现实

> UI 决定"看到什么"，通道决定"够不够得到"。这一层的全部问题可以压缩成一句话：**手机和 PC 不在同一网络时，怎么建立一条可信的到达路径？** DSH 生态给出了教科书级的方案谱系——从零配置隧道到为 CGNAT 定制的自愈管道。

---

## 1. 通道选型的四个变量

任何到达方案都在四个变量上取舍：**延迟**（直连 < 内网穿透 < 公网中转）、**固定性**（地址会不会变）、**零配置程度**（要不要自己有服务器/域名）、**信任根**（流量经过谁的手）。逐个看生态里的答案。

## 2. SSH 反向隧道：自己服务器的确定性

Guuu16/dsh-remote 的哲学写在标题里："**同一个 runtime，不是第二个视图**"——手机打开的就是真实的 DSH Web GUI，同一份工作区、同一份聊天记录，不做任何代理视图。

它的 SSH 反向隧道工程值得抄：

- 插件自动化了整套配对：**ssh-copy-id、验证密钥、从磁盘清除密码**，然后建立 `ssh -R` 隧道；
- **断线每 5 秒重拨**；
- 两种通道同插件可选：SSH 反向隧道（用自己的服务器，延迟低）或 Cloudflare 隧道（零配置，临时 `*.trycloudflare.com` 域名）。

SSH 反向是"有自己的 VPS"用户的甜点：确定性最高、信任根是自己的服务器，代价是要养一台机器。

## 3. Cloudflare：零配置的两副面孔

- **临时隧道**（Quick Tunnel）：一条命令得到 `*.trycloudflare.com` 域名，零配置零账号——但地址随机、性能不保证、匿名传输；
- **Named Tunnel**（固定域名）：需要账号与域名，地址固定、可配访问控制——StyleJeke/dsh-tunnel-plugin 与 dsh-bridge 都把它做成"设置页一键启停"，并补上 cloudflared **意外退出自动重连**（StyleJeke 最多重试 6 次）。

两副面孔的分工在生态里很清晰：临时隧道当"应急通道"，Named Tunnel 当"日常通道"。**通道的临时性必须与认证的强度联动**——下一层的主题，但通道层的项目已经自觉配合：dsh-webgate 明确把 cloudflared 定位为"临时应急"。

## 4. frp：自有基础设施的固定地址

dsh-web-remote-frp（dsh-web-remote 的 frp 版本）代表第三条路：**frpc → 自己的 frps 服务器**，用一台有公网 IP 的机器换固定域名/固定地址，速度与稳定性自主可控。工程细节：

- 支持 tcp/http/https 三种代理模式；
- **frpc 缺失时自动从 GitHub Releases 下载**——把"通道组件的安装"也插件化；
- 安全侧随机令牌、HttpOnly Cookie，局域网可免 token。

与 Cloudflare Named Tunnel 的对照是一条经典的私有化分界线：**frp 的信任根是自己的服务器，Cloudflare 的信任根是 Cloudflare**。saya-ch/dsh-mobile 把选择权做到最宽：局域网、Tailscale Funnel、cpolar、cloudflared、自建 FRP、自有反向代理全部可选——多通道并存 + 每通道独立安全策略（08 篇：私有 CA 只在局域网信）。

## 5. CGNAT 现实：dsh-phone-access 的痛点方案

家庭宽带的残酷现实是 **CGNAT**（运营商级 NAT）：没有公网 IP，SSH 反向和 frp 都需要一台公网机器。dsh-phone-access 解决的是这个场景里一个**非常具体**的痛点：

> DSH 重启后手机访问入口失效。它在 DSH 每次启动时**等待 20 秒**，检查手机端端口和 cloudflared 进程，缺失则**重建隧道与 web 实例，并把新链接发到邮箱**。

三个设计决定都值得记：**无常驻进程**（挂靠 DSH 启动生命周期，不自己驻留）；**接受链接会变**（重建后新地址走邮件——不为了固定地址引入永久基础设施）；明确定位"电脑长期开机、手机作为输入查看终端"的家庭场景。**承认约束、把重建自动化、用邮件送达新地址**——小而完整的工程闭环。

## 6. Tailscale：把"组网"外包出去

Tailscale 在生态里是特殊存在：它不是隧道插件，而是**把"同一网络"本身重建出来**（WireGuard mesh）。dsh-Remote 支持局域网/Tailscale 直连，bluelightgit/dsh-remote-access 把"Tailscale 私有入口"与 LAN HTTPS、Cloudflare Tunnel 并列为三通道（10 篇）。它的甜点：设备间直连、无需公网组件、信任根是自己的 tailnet——代价是每台设备都要装客户端、依赖第三方协调服务。

## 7. 通道层对照表

| 通道 | 固定性 | 零配置 | 信任根 | 甜点场景 |
|---|---|---|---|---|
| 局域网直连 | 局部 | ✅ | 自己 | 家里日常 |
| Tailscale | ✅ | 近似 | 自己的 tailnet | 多设备私有网 |
| SSH 反向 | ✅（自己的 VPS） | 需 VPS | 自己 | 延迟敏感 |
| Cloudflare 临时 | ✗ | ✅✅ | Cloudflare | 应急演示 |
| Cloudflare Named | ✅ | 中 | Cloudflare | 日常公网 |
| frp | ✅（自己的 frps） | 需 frps | 自己 | 固定地址自主可控 |
| dsh-phone-access | ✗（邮件送达） | ✅ | Cloudflare | CGNAT + 长期开机 |

## 8. 边界与不足

通道层**不解决身份**——所有隧道都只是"把端口搬过来"，配对/认证/授权全在安全层（10 篇）；"同一个 runtime"哲学下，隧道断线 = 手机端整体不可用（没有离线缓存，对比 dsh-Remote 的聊天离线查看是 UI 层补的）；Tailscale/cpolar/Cloudflare 都引入第三方依赖，"数据只在你的设备之间流动"的承诺强度取决于信任根声明与实际路由是否一致——这要靠下一层验证。

## 9. 一句话总结

> 通道层的全部智慧是"解耦"：到达路径与身份认证解耦、临时应急与日常固定解耦、通道组件的安装与运维解耦——每条隧道只负责"把端口搬过来"，其他的一概不装懂。
