# 远控安全层——三道门、边界代理与网关白名单

> 通道把端口搬到了公网，安全层回答的问题是：**谁可以进来，进来之后能碰什么。** 上一轮写作时，"三道门"只是对一个项目 README 的转述；这一轮克隆了两个代表性项目读完源码——StyleJeke/dsh-tunnel-plugin 的边界代理和 bluelightgit/dsh-remote-access 的 API 网关——原理从此有代码背书。

---

## 1. 三道门：DSH 自己的防线

agent 的 Web 服务在 PC 上监听时，自带三道门：

1. **Host/Origin 栅栏**：`/api` 的浏览器信任栅栏只接受回环地址或启动时声明的 `--trusted-host`；
2. **会话 cookie 绑定**：DSH 每次进程启动生成内存随机 `?token=`，凭据与会话绑定在建立时的上下文；
3. **审批闸门**：会话内危险操作要过审批（01 篇解剖过的那个闸门）。

## 2. 边界代理的源码：StyleJeke/dsh-tunnel-plugin

克隆读 `lib/index.js`（640 行），头注释把整个项目的存在理由写成了三行（原话）：

> 1. 把 `Host` / `Origin` **重写成回环权威**。DSH 的 `/api` 浏览器信任栅栏只接受回环或启动时声明的 `--trusted-host`，而隧道投递的是公网主机名——**只改 Host 不够，`Origin` 必须同时匹配，否则 WebSocket 握手会被 403**。
> 2. （抓取 DSH 进程启动生成的内存 `?token=` 随机数，**铸造 cookie 并注入**。）
> 3. 用一次性访问密钥（`?k=...` 换 cookie）把守入口。因此**这层代理是唯一的口令关卡**。

三件事拆开：

- **Host/Origin 双重写**：README 有一张实测教训表——"直接把隧道指向 `127.0.0.1:3080` 是不行的"，而且"**只改 `Host` 不够——回环 Host + 外部 Origin 实测同样是 403**"；"只重写 `Host` 是行不通的。这是整个项目存在的理由，也是我实测撞到的第一个 403"。两个头必须**一起**改写成回环权威，栅栏才放行；
- **cookie 铸造**：代理启动时从 DSH 进程抓取内存 token，作为 cookie 注入给通过认证的客户端——即上一章说的"铸造合法会话 cookie"的代码形态；
- **一次性入口密钥**：`?k=...` 只出现一次，换出 cookie 后不再走 URL——token 不随外链泄漏。

`lib/index.js` 里还有两条**实测撞出来的边角知识**（注释原文）：

- "同源校验别拿 `Origin` 去比 `Host`——**cloudflared 会把 `Host` 改写成源站地址，两者永远不等**；另外浏览器在沙箱上下文等情形会发 `Origin: null`，那是合法请求"；
- cloudflared 的两种模式：Quick Tunnel 用 `tunnel --url <origin>`（临时 `*.trycloudflare.com`），Named Tunnel 用 `tunnel run --url <origin> --name <name>`，固定域名从 cloudflared 的配置文件直接读 hostname 而不是解析日志（"文件不存在则退回快速隧道"）。

**这层代理对本博客有特殊意义**：它与 reverse-proxy 系列（系列二）是同一个原理的自反应用——重写协议头 + 铸造会话凭据，那次逆向闭源客户端的私有协议，这次给自己的 agent 做协议适配。

## 3. 网关白名单的源码：bluelightgit/dsh-remote-access

`api-gateway.js`（704 行）把"谁进来之后能碰什么"做成了**具名方法白名单**：

```js
export const DEFAULT_BASIC_API_ALLOWLIST = Object.freeze([
  'respond', 'agentPreset.list', 'goal.create', 'host.describe',
  'llm.models', 'session.prompt', 'session.cancel', 'session.history',
  'workspace.create', 'subagent.prompt', 'skill.list', ...
])   // 39 个具名方法

// Public transport modes with no user authentication (notably Cloudflare
// Tunnel-only) are limited to this reviewed read-only subset. Mutating state
// or driving an agent requires switching that ingress to an authenticated
// mode first.
export const DEFAULT_READONLY_API_ALLOWLIST = Object.freeze([...])
```

三个设计决定值得学：

1. **白名单按方法名而非 URL 路径**——`session.prompt` 与 `session.export` 是两个独立的授权单元，粒度到"能做什么"而不是"能访问哪个路径"；
2. **匿名传输的只读子集**：`ACCESS_MODES = ['lan', 'serve', 'funnel', 'cloudflare']` 四种通道模式各有策略，**funnel（公网）默认更严**——`trustedRemoteSettings: false`、写方法全部剔除；注释明说"匿名公网传输只能用这个只读子集，要变更状态或驱动 agent 先切到认证模式"；
3. **网关自有头传递信任态**（"Preserve the trusted ingress mode in a gateway-owned header so DSH can ..."）——网关对上游隐藏真实的入口模式细节，下游只信网关的判断。

配套 `request-security.js` 的 Host/Origin 规范化是 fail-closed 的教科书（注释原话）："Invalid or repeated values return an empty string **so callers fail closed** instead of comparing partially parsed strings"——解析失败的 Host 直接等于空串，绝不拿半解析结果去比较。Origin 的校验更严：带路径、query、fragment、凭据或非 http(s) scheme 的一律无效。

## 4. 认证纵深与诚实边界

网关族其余成员的机制（README 口径）：dsh-remote-mobile——扫码配对、长期密码、**登录凭证 RSA 加密**、**scrypt 慢哈希落盘**、连续输错自动**熔断锁定 IP**、SSE 推送安全事件，并诚实标注"**插件本身不提供全链路 TLS**，完整传输加密需依赖 Tailscale 或外层 HTTPS"；dsh-bridge——微信/QQ/飞书/Telegram 机器人矩阵、访客密码门、管理员防篡改锁、127.0.0.1 应急重置；dsh-webgate——三模式门户、30 天 HttpOnly Cookie、每 IP 限速、iOS Safari Basic Auth 弹框死循环修坑。

四条通用模式：**边界代理是协议适配器**（§2）、**默认拒绝 + 按通道分级白名单**（§3）、**认证纵深**（慢哈希 + 加密 + 熔断 + HttpOnly 各挡一击）、**诚实边界**（认证与加密、通道与身份的解耦声明）。

## 5. 项目锚点：两个自研项目的安全层

- **星渡远程模式**（04 篇）：极简——"应用不创建 VPN、不配置远端 DSH，也不开放主机公网端口"；App 侧只做 URL 策略（`RemoteUrlPolicy`）；局域网连通已真机验收，Tailscale **未验证**并如实标注；
- **DSHA 的 LAN 访问**：源码对应 `LanAuth.java` / `LanProxyService.java`——token 鉴权 fail-closed，"命中后回设 SameSite=Strict Cookie"；安全模型明说"LAN HTTP 是明文；不提供 TLS、受信配对"。

两者都选择"**不重造网关**"——把公网发布外包给 Tailscale/网关族，自己只守端点策略。分工：**App 守 origin，网关守协议，隧道守可达**。

## 6. 边界与不足

网关族均无第三方渗透测试；白名单"默认集"的宽严没有跨项目标准（bluelightgit 的 39 个方法是逐一审过的具名清单，其他项目多为路径级）；IP 熔断在 NAT 共享出口下会误伤；"三道门"的 DSH 侧实现本系列未直接读（deepseek-harness 上游仓库体量大，未克隆）——本章的 DSH 行为描述以 StyleJeke 的实测注释（403 场景）与网关项目的适配代码为交叉证据；网关与 DSH 版本对齐依赖社区跟进。

## 7. 一句话总结

> 安全层的全部智慧浓缩成一个原理和一条纪律：边界代理负责让请求"合法"（Host/Origin 双写 + cookie 铸造，实测教训比文档贵），白名单负责让请求"最小"（具名方法、按通道分级、fail-closed）——而每一层都要诚实说出自己**没有**做什么。
