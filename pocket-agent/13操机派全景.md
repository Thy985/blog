# 操机派全景——当手机成为 Agent 的身体

> 前两个家族里，手机是 agent 的宿主（本机派）或遥控器（远控派）。操机派翻转了关系：**手机是被操作的对象**，agent 坐在模型端，用眼睛看屏幕、用手指点界面。这一章看这个家族的技术谱系、它和编程 agent 的分野，以及 DSHA 设备桥踩出的杂交路线。

---

## 1. 操机派在做什么

任务形态："帮我在机票 App 订一张明天的票"、"把这个 App 里的表格导出来"。agent 的循环是：

```
截屏/读屏 → 多模态理解（这是什么界面、可点什么）→ 决策动作 → 执行（点击/滑动/输入）→ 循环
```

它本质上是 **Computer Use 的手机版**：与桌面 browser-use 同构，难点在移动端特有——小屏密集 UI、应用内 WebView 混合渲染、系统级权限弹窗、跨 App 任务流。

## 2. 技术谱系：两代技术栈

| 代际 | 感知 | 动作 | 代表 |
|---|---|---|---|
| 第一代（结构化） | 无障碍树 / view hierarchy | 直接调用结构化 API（按 ID/文本点按） | AppAgent 早期、uiautomator2 方案 |
| 第二代（视觉端到端） | 截图 → 多模态模型 | 坐标级点击/手势 | UI-TARS、Mobile-Agent v2/v3、AutoGLM |

- **[AppAgent](https://appagent-official.github.io)（腾讯）**：开山之作之一，"作为智能手机用户"的多模态 agent——通过探索阶段建立"哪些 UI 元素对应什么功能"的动作文档，再执行；
- **Mobile-Agent 系列（X-PLUG）**：探索式操作框架的持续迭代（规划-反思-工具调用多 agent 协作）；
- **UI-TARS（字节）**：原生 GUI 自动化模型——把"看屏 → 出坐标动作"端到端学进一个模型，AndroidWorld 类基准的常客基线；
- **AutoGLM（智谱）**与 2026 手机 AI（豆包手机等）：从研究走向手机产品化——但闭源为主，社区可复现的是框架层；
- **[DroidRun](https://github.com/droidrun/mobilerun)**：开源框架层，"给 LLM agent 手机原生工具"（读 UI 状态、交互、App 生命周期），自称"AI agent 的手机层"——操机派里的"框架供应商"，与 UI-TARS 这类"模型供应商"分层。

**两代栈的分野**在 06 篇已经用 DSHA 源码踩过一遍：结构化信息（无障碍树）把语义层的活提前做掉，可靠性高但上限锁死；视觉端到端通用性强但每一步都是概率——**可靠性 vs 通用性的经典权衡**。

## 3. 基准：怎么评一个操机 agent

- **AndroidWorld**（Google）：标准虚拟设备 + 任务集，看任务完成率——社区事实基准；
- **Android Agent Arena (A3)**：带开源评测流水线（AITK）的新一代基准；
- 共同问题：**任务完成率的方差极大**——同一模型跨机型、跨 App 版本、跨语言环境的分数不可直接比，论文间数字横向对比尤其要小心。

## 4. 与编程 agent 的分野

表面都是"agent + 工具环"，深层有三处不同：

1. **成功判据**：编程 agent 有编译器/测试当验证器（RLVR 传统）；操机派的成功判据经常是模糊的（"订到票"怎么程序化验证？）——奖励信号稀缺，这直接决定了它更依赖模仿学习而非 RL（呼应 embodied-ai 系列 13 篇）；
2. **动作空间**：编程 agent 的动作是"结构化的工具调用"，操机派的动作是"屏幕坐标 + 手势"——动作空间越连续，验证和重放越难；
3. **风险面**：编程 agent 搞坏的是代码库（可 git 回滚），操机 agent 搞坏的是真实数字生活（误发的消息、误删的照片不可回滚）——**审批与确认在操机派里是生死问题而非体验问题**。

## 5. 项目锚点：DSHA 设备桥——杂交路线的实证

06 篇已从源码层面读过 DSHA 的设备桥，这里放回本谱系定位：它是**编程 agent × 操机派的第一代栈**——

- 无障碍树结构化输出（带可点击区域坐标）= 第一代感知（`DshaAccessibilityService.java`，563 行）；
- `DeviceShellPolicy` 的类型化白名单 + `[POLICY_BLOCKED]` = 编程 agent 的审批文化移植到设备操作；
- agent 本体是 DSH（编程 agent），设备操作只是它工具箱里的一组端点（127.0.0.1:3090）。

这个杂交的启示：**操机派不必从视觉端到端开始**——当 agent 已经拥有一个可编程的宿主（本机派的 Ubuntu 环境），结构化设备桥是性价比极高的第一步。反过来说，视觉端到端（UI-TARS 路线）的不可替代场景是"没有宿主、没有无障碍授权"的纯外部操作。

星渡的反向选择也在此显影：截图/录屏**默认保护**、设备能力桥不做——它把"agent 拥有手机"这个方向整体划出边界，专注本机执行。**同为 DSH 安卓壳，两个项目在"要不要让 agent 碰这台手机"上给出了相反答案**——这本身就是 15 篇决策表的一个维度。

## 6. 边界与不足

操机派的开源程度两极分化：框架层（DroidRun）与研究原型（AppAgent/Mobile-Agent）开源，产品级（AutoGLM、豆包手机）闭源；基准分数跨论文不可比（§3）；隐私是家族级难题——读屏意味着把屏幕内容交给模型，"哪个 App 的哪些屏可以给哪个模型"没有生态级共识；Android 的无障碍权限被滥用史（恶意软件）使系统与厂商对它持续收紧，第一代栈的通道本身在变窄。

## 7. 一句话总结

> 操机派把手机变成 agent 的身体，代价是把最难的验证问题（"做对了吗"）和最重的责任问题（"做错了算谁的"）一起接了过来——DSHA 的设备桥示范了用结构化通道换可靠性的杂交路线，而它的尽头是视觉端到端的通用性。
