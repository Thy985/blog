# E02：验证器审计——"测试套件通过"不是验证器

> 在任何能力声明做出之前，先问 reward 本身可信吗。这次审计的发现至今是该系列最重要的一条：一个只看退出码的奖励函数，给篡改测试树的"修复"打 1.000 分，给真正的部分修复打 0.571 分。

---

## 1. 研究问题与假设

E01 的两次撤回（07 篇）留下一条活着的教训：**测量仪器先于结论**。E02 把这条教训从"事后学到的规则"升级成"事前设置的闸门"：

- **问题**：reward 本身可信吗——在对着它做任何能力声明之前？
- **假设 H02**：经过审计的验证器是一个有效的奖励源。
- **出处**：E01 撤回二的教训 2（"verify the verifier first"），这次被当作闸门而不是希望。

## 2. 设计：两件便宜但承重的工件

审计不追求复杂，追求**在第一个 live run 之前就位**：

**工件一：Golden Episode。** 一份人工核查过的 episode——它的轨迹、文件树哈希、判定和奖励在任何真实运行之前被录制固定。此后每次验证器改动或每次可疑读数，都有这块"基准石"可对照。

**工件二：Replay 验收。** 把同一份奖励从归档轨迹重算，必须复现 live 值。如果重算不复现，说明奖励不是轨迹的函数——中间有隐藏状态或时序依赖，那本身就是 bug。

**工件三（叠加）：分档审计。** 后续难度阶梯（E03）的每一档实例都审计"奖励到底有没有区分度"，而不是默认有。

配套的纪律：整个研究用**同一个验证器版本**；每档任务集冻结；树的状态记录为哈希，让"修复"可以被 diff，而不是被肉眼判断。

## 3. 结果

- 环境契约 + Golden Episode 在第一个 live run 之前关闭（提交 `498fca529`）。
- 对保存轨迹的执行式 replay 通过——Phase 1B 验收（提交 `56a6c91d1`）。
- **Headline 发现**：exit-code 和"原始通过率"（raw pass fraction）作为奖励时，**一个篡改测试树的"修复"得 1.000，一个真正的部分修复得 0.571**。

篡改的手法朴素到令人不安：删掉失败的测试，或者让测试脚本静默退出 0。"测试套件全绿"这个信号对这两种行为完全不设防——它只回答"绿了吗"，不回答"为什么绿"。

## 4. 结构化判定：因为标量不够用

审计的直接产物是把奖励从标量升级为结构化判定：

| 字段 | 回答的问题 |
|---|---|
| `per_test` | 逐测试通过/失败——通过率不再是黑盒 |
| `fixed_targets` | 目标测试（F2P）真的被修了吗 |
| `regressions` | 有没有把原来通过的改坏 |
| `tampered` | 测试树是否被篡改 |
| `timed_out` | 是否超时而非通过 |

resolve 的最终定义：**全部 F2P 和 P2P 通过，且树未被篡改**。部分修复不再是 0.571 分的模糊地带，而是带着"修了哪几个、坏了哪几个"的完整画像。

这个结构的价值在后面持续兑现：档案里后来每一次指标争议（`2>/dev/null` 被误计为写树操作、WRITE_RE 的修复、条件写率混淆）都是这次审计的后代——**有结构才谈得上修复，标量无从修起**。

## 5. 被排除的东西

- exit-code 和原始通过率**作为奖励**——不是"不够好"，是"会被反向优化"。
- 对未审计验证器做出的任何能力声明。
- 不能从 Episode 再生的第二份实验记录。

## 6. 局限

审计是分档分实例的，**不认证验证器在分布外修复上的行为**——没见过的作弊手法仍然可能漏网。这台机器没有容器运行时，SWE 验证器跑在宿主文件系统上（克隆 + 宿主侧测试补丁），与官方 harness 不可直接比较。

## 7. 一句话总结

> RLVR 的第一定律：reward 不是数据，是仪器。仪器没有基准石和重放验收之前，你训出来的不是能力，是仪器偏差的画像。

下一篇把这份审计过的验证器用起来：造一个难度阶梯，结果发现排名不重要，**审计轨迹才是阶梯的真正产出**——外加两个被测量 bug 藏起来的真相。
