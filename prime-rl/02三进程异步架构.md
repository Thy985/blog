# 三进程异步架构——inference、orchestrator、trainer 如何各自为政

> prime-rl 的一个 RL run 是三个协作进程：一个管生成，一个管调度，一个管学习。它们步调不同、节奏各异，靠消息和权重广播咬合成一条永远不空转的流水线。

---

## 1. 三个进程的分工

读 `docs/overview.md` 和 `src/prime_rl/` 的目录结构，职责划分一目了然：

| 进程 | 职责 | 代码位置 | 硬件画像 |
|---|---|---|---|
| **Inference** | 持有当前策略的 vLLM 服务（或集群），生成 rollout | `src/prime_rl/inference/` | GPU 密集，吞吐优先 |
| **Orchestrator** | CPU 进程，数据面总管：驱动环境 rollout、算优势、打训练批次、中继权重 | `src/prime_rl/orchestrator/`（约 40 个模块，主循环 `orchestrator.py` 1077 行） | 无 GPU |
| **Trainer** | FSDP2 进程组，消费打包好的 rollout，步进优化器 | `src/prime_rl/trainer/` | GPU 密集，计算优先 |

环境（environments）不是第四个进程，而是 orchestrator 管理下的一池子**子进程**：每个训练源（`[[orchestrator.train.source]]`）对应一个 `env-server`，内部有可变大小的 env worker 池。入口 `entrypoints/` 里能数出全部角色：`rl.py`、`sft.py`、`inference.py`、`orchestrator.py`、`trainer.py`、`eval.py`、`env_server.py`、`dashboard.py`。

`uv run rl @ rl.toml` 这一个入口做的事：把合并的 TOML 拆成每进程子配置，按 GPU 顺序分配（先 inference 后 trainer），拉起三个进程 + 每个源一个 env-server（各绑一个本地回环端口），并把所有 stdout tee 进 `<run_dir>/logs/`。

## 2. 异步流水线：永远错开一步

同步 RL 框架的循环是：

```
rollout(π_old) → [全部收齐] → train 一步 → 同步权重 → rollout(π_new) → ...
```

trainer 和 inference 串行，谁也别想跑满。

prime-rl 的默认是**完全重叠**的错步流水线（`docs/algorithms.md` §Async/Off-Policy）：

- 第 n 步，**trainer** 用第 n 批 rollout 训出 θ_n；
- 同一时刻，**inference** 用 π_{n-1}（上一步的权重）生成第 n+1 批 rollout。

只要两侧单步耗时相近，就没有任何一方在等待——这是流水线并行，不是加速技巧，而是把"rollout 慢于训练"的长尾（智能体任务的多轮工具调用）摊平到每一步里。

代价在 01 篇说过：第 n 批数据是 π_{n-1} 生成的，天然 off-policy 一步。prime-rl 不假装这个问题不存在，而是把它做成可调可观测的旋钮：

- `orchestrator.max_off_policy_steps`（默认 8）：一批 rollout 从生成它的策略版本到被训练时的**最大年龄**（含排队时间）。超龄的整组丢弃。想吞吐就调大，想贴紧 on-policy 就调小。
- 配套监控 `off_policy/*` 和 `mismatch_kl/*`（04 篇）：前者看年龄分布，后者直接度量"训练时的策略和生成时的策略差了多远"——这是 off-policy 崩溃的早期预警。

一组 rollout 共享同一个 dispatch 版本号，所以整组同生共死，不会出现组内一半新鲜一半陈旧的脏批次。

## 3. 传输层：消息走 ZMQ，权重走 NCCL

三进程之间的通信在 `src/prime_rl/transports/` 里，按用途分两类，各自可插拔：

**rollout 链路（orchestrator ↔ trainer）**：默认 ZMQ（`transports/batch/zmq.py`），可切文件系统（`rollout_transport.type = "filesystem"`，rollout 落盘，适合调试或跨机共享存储）。

**权重广播（trainer → inference）**：默认 NCCL 同步内存拷贝（`transports/weights/nccl.py`），LoRA 或无推理服务时回退文件系统；大规模场景可换 NIXL（`transports/weights/nixl/`，InfiniBand 直传，接收端拉取式 + 双 arena 重叠传输与重放）。

这里有个容易被忽略的设计：inference 进程**完全无状态**。它不存训练进度，重启时从最新 checkpoint 重新推权重即可。也因此 checkpoint 分进程保存（06 篇）——trainer 存模型/优化器/调度器，orchestrator 存进度和环境数据状态，两者可以在不同机器、不同步数上。

## 4. Orchestrator：数据面操作系统

如果只读一个模块理解 prime-rl 的设计，读 orchestrator。它不训练任何东西，但管着数据面的一切：

- **环境子进程池**：每个环境隔离跑在子进程里（`orchestrator/envs.py`、`eval_source.py` / `train_source.py`），worker 池大小可调，环境崩溃不炸主进程。
- **rollout 生命周期**：驱动多轮 rollout（工具调用、浏览器、沙箱），跨轮**不重分词**（这是 renderers 的活，05 篇）、算优势（algo 钩子）、过滤无信号样本、打包训练批次（`packing.py`、`dispatcher.py`）。
- **自适应并发**：`concurrency.py` 根据推理服务压力动态调在途 rollout 数量，SFT 的在线 eval 也复用同一控制器。
- **curriculum**：每个训练源可以配采样器 + 准入门（03 篇）。
- **信号过滤与补齐**：全零优势的样本默认被过滤，且 orchestrator 会继续收集补齐批次（`constant_trainer_batch_size = true`），保证 trainer 每步吃到固定数量的有效 trace——这是一个只对异步系统才存在的概念：trainer 的批次是"凑"出来的，不是"等"出来的。

## 5. 互为瓶颈的两大指标

异步系统里最反直觉的观测点：**两个等待时间互为镜像**。

| 指标 | 来源 | 高了说明 |
|---|---|---|
| `time/wait_for_batch` | trainer | orchestrator 是瓶颈 → 加 inference 节点 |
| `time/wait_for_policy` | orchestrator | trainer 是瓶颈 → 加 trainer 节点 |

trainer 等批次超时会自己告警，orchestrator 等新权重同理。扩容方向不是猜的，是读出来的。这个设计把"异步系统运维"从玄学降维成两个数字。

## 6. 一公里长的日志树与本地 dashboard

`<run_dir>/` 的布局值得单独一提（`docs/training.md` §Observability）：

```
outputs/<run_name>/
├── configs/attempt_N/resolved/   # 每次启动的解析后配置
├── logs/latest/                  # trainer/orchestrator/inference/eval + envs/*
├── checkpoints/step_N/           # 分进程 checkpoint
└── monitors/file/metrics.jsonl   # 所有指标，一行一条
```

`uv run dashboard` 起一个本地 web（默认 7788 端口）：指标面板、rollout trace viewer（带 per-token 的 advantage / entropy / mismatch 叠加层）、合并日志。它只读 run 目录，可以对着正在跑的训练开——在我单卡的实验里，trace viewer 是排查"这个 rollout 为什么拿了 0 分"的最快路径。

## 7. 与同步框架对比：一个表格

| | 同步循环（TRL 式） | prime-rl 异步 |
|---|---|---|
| on-policy 程度 | 严格 on-policy | 错 1 步起，可调上限 |
| 硬件利用率 | rollout 与 train 互等 | 完全重叠 |
| 适合任务 | 单轮、rollout 快而稳 | 多轮、agentic、长尾分布 |
| 系统复杂度 | 低 | 高（传输层、staleness、补批） |
| 崩溃半径 | 全停 | 环境子进程隔离、超龄丢弃 |

一个值得记住的判断：**异步不是优化，是把"rollout 时间的方差"从系统里挤出去的方式**。同步循环里，最慢的那条 rollout 决定每步的时间；异步流水线里，慢 rollout 只是让那批数据晚点被训（在 staleness 上限内），不阻塞别的数据。

## 8. 一句话总结

> 三个进程、两种传输、一个数据面操作系统。异步 RL 的架构问题不是"怎么并行"，而是"怎么在允许偏差的前提下，让每一步都知道自己偏了多少"。
