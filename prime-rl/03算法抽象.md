# 算法抽象——为什么 trainer 不认识 GRPO

> 在 prime-rl 里加一个新 RL 算法，不改 trainer、不改打包、不改热路径。秘诀是把"算法"降维成一种数据格式：每个 token 三个数字——它属于哪个损失组件、权重多少、优势是多少。

---

## 1. 一个反直觉的设计

大多数训练框架的 RL 算法实现长这样：`Trainer` 类里有一堆 `if algo == "grpo": ... elif algo == "reinforce": ...`，梯度计算、KL 惩罚、优势归一化搅在训练循环里。加新算法 = 改核心类。

prime-rl 的文档里有句话值得刻在墙上：

> **The trainer is algorithm-blind.**（trainer 对算法无感知。）

trainer 只知道损失是三个组件的和：

$$\mathcal{L} = \frac{\sum \mathcal{L}_{rl}}{N_{rl}} + \frac{\sum \mathcal{L}_{ce}}{N_{ce}} + \frac{\sum \mathcal{L}_{ref\_kl}}{N_{ref\_kl}}$$

- `rl`：RL 损失（默认 IPO，见 04 篇），吃优势流
- `ce`：掩码交叉熵，吃"冻结模型生成的 token"（SFT 蒸馏）或"环境给的观察 token"（ECHO）
- `ref_kl`：对参考模型的逐 token reverse KL，吃参考 logprobs（on-policy 蒸馏）

orchestrator 在每个样本上盖三个 per-token 权重流（`rl_weights` / `ce_weights` / `ref_kl_weights`）加一个优势流（`advantages`），顺着网络发给 trainer。**所谓"算法"，就是这套流的填充规则。**

关键细节：三个组件**各自用自己的全局 token 数归一化**。加 ECHO 的观察 token 进 ce 组件，不会稀释 rl 项的有效学习率；一个 SFT 环境和一个 GRPO 环境打包进同一个 micro batch，SFT 的梯度也不会被 GRPO 的规模软化。每个 token 的 (组件, 权重) 二元组就是它的全部训练语义。

## 2. 模型引用：policy 与冻结端点

算法抽象的另一半是"从哪采样"。prime-rl 只托管一个模型——可训练的策略。算法需要的其他模型一律是**外部 OpenAI 兼容端点**，声明在使用它的组件上：

```toml
[orchestrator.algo]
type = "opd"

[orchestrator.algo.teacher]   # opd 的教师：被它打分的冻结模型
name = "Qwen/Qwen3-32B"
base_url = "http://localhost:8001/v1"
```

模型引用只有两种：字符串 `"policy"`（活策略），或 `{name, base_url}`（冻结托管模型）。文档造了一个词叫 **liveness**（活性）——它是引用的属性，不是角色的属性：

- 从 `"policy"` 采样的 rollout，前缀缓存**按版本加盐**（权重一更新缓存即失效），携带采样 logprobs 供重要性修正，随训练**老化**（off-policy 化）。
- 从冻结模型采样的 rollout，前缀缓存稳定，永不老化。

角色词汇是算法局部的：`opd` 叫它的模型 `teacher`，`sft` 的教师就是它的 `sampling.source`，`opsd` 自蒸馏（教师就是活策略）根本没有模型字段。调度器和 trainer 只判断"活/冻"，不关心你管它叫什么。这个区分是类型级的：`opd` 的 teacher 类型是 `FrozenModelConfig`，写 `"policy"` 直接被拒——因为 KL 恒为零，是退化配置。

## 3. 八种算法，一张表

`[orchestrator.algo] type` 命名算法，类默认值即其"验证过的配方"——只写 type 不写别的键，就是那个算法本身：

| `type` | 采样 | 损失组件 | 一句话 |
|---|---|---|---|
| `grpo`（默认） | policy | rl | 组相对 RL：奖励减组均值 |
| `max_rl` | policy | rl | GRPO 用组均值归一化替代 std，上加权难例（MaxRL 论文） |
| `rae` | policy | rl | SPIRAL 的角色条件优势：每个 agent 减自己的 EMA 基线，自博弈环境用 |
| `hierarchical_grpo` | policy | rl | 提题-解题环境：解题者组内比，提题者跨提案比 |
| `echo` | policy | rl + ce | GRPO 之外，对环境观察 token 按角色加权做 CE（默认工具返回值，α=0.1） |
| `opd` | policy | ref_kl | on-policy 蒸馏：学生采样，逐 token reverse KL 对教师（Thinking Machines） |
| `opsd` | policy | ref_kl | SDFT：以专家示范为条件，学生是自己的参考——自蒸馏，零额外部署 |
| `sft` | 冻结教师 | ce | 硬蒸馏：教师生成，学生在其 token 上做 CE |

## 4. 写一个新算法：两个钩子

算法基类在 `src/prime_rl/orchestrator/algo/base.py`，每个算法一个模块（`algo/grpo.py`、`algo/opd.py`……）。两类打分钩子对应两种时序：

- `score_episode(episode)` — 单条 rollout 到达时的局部打分（OPD 在这里查教师 prefill，逐条流水，不攒批）
- `score_group(episodes)` — 一组到齐后的组相对打分（GRPO 家族都在这里）

写新算法 = 继承 `Algorithm`、覆盖钩子、调用 `assign_advantages(trace, advantage)` 把优势标到轨迹图上，然后在 `ALGORITHM_CLASSES` 注册、把配置加进判别联合。共享数学（长度惩罚、prefill 对齐）是 `algo/advantage.py` 里的普通函数。文档强调：**没有"配置指向用户代码"的钩子**——新算法是仓库里的具名类，不是 import path 字符串。这是一种立场：算法是代码审查的对象，不是插件市场的商品。

## 5. 每个环境一个算法

两个维度都是 per-env 解析的：每个训练源继承顶层 `[orchestrator.algo]`，也可以自带一个。于是一个 run 可以数学环境跑 GRPO、终端环境跑 ECHO：

```toml
[[orchestrator.train.source]]
name = "math"
algo 不写 → 继承顶层 grpo

[[orchestrator.train.source]]
name = "terminal"
algo.type = "echo"
```

`rae` 算法的实例还是 per-(env, agent) 的——EMA 基线按环境加 agent 键控，重启后按 `1/(1−decay)` 条轨迹重新暖机。这些有状态的东西的 `state_dict` 进 orchestrator 的 checkpoint。

## 6. Curriculum：采样器与准入门

每个训练源配一个 curriculum：一个任务采样器 + 若干准入门。组被所有门放行才训练，被拒的组保持可观测，orchestrator 继续采样补批。内置三件套：

- `StandardSampler`：默认，顺序推进任务迭代器
- `DifficultyPoolSampler`：按组奖励把任务分进 hard/normal/easy 池，每池配权重——难池权重 0.2、正常池 1.0 这种"课程表"
- `AdvRangeGate`：拒绝所有可训练 token 的优势都落在 `reject_min..reject_max` 里的组——即"这组全是白跑的，别训"

这解决的是 RLVR 的经典病：任务太简单（全对，优势全零）或太难（全错）都在浪费算力。curriculum 把"什么任务值得训"从写死的策略变成可观测可调的采样逻辑。

## 7. 无信号样本与批次补齐

orchestrator 会过滤掉没有训练信号的样本——典型是全零优势。注意这是**异步系统里特有的决策点**：trainer 的批次是凑出来的，那么被过滤后是凑数补齐（`constant_trainer_batch_size = true`，默认），还是接受变小批（false，吞吐更高但 trainer 批次不定）？

prime-rl 默认补齐：trainer 批次大小恒定，梯度估计的噪声特性可预期。代价是 orchestrator 多采样。文档诚实地标注了 trade-off——这是这个代码库的一贯风格：每个默认值旁边写清楚关掉它的理由。

## 8. 一句话总结

> 把算法从"训练循环里的分支"变成"wire 上的三个 per-token 流"，新算法就再也不用碰热路径。好抽象的标志是：最复杂的新东西，落在系统里最安静的地方。
