# 任务编排——行为树、状态机与 LLM 规划

> 运动规划解决"怎么去"，任务编排解决"接下来做什么"：先侦察再抓取、抓失败重试、超时换策略。这一层的工程主角是行为树——以及一个它绕不开的现代命题：LLM 能不能取代它。

---

## 1. 三种编排范式的竞争

**有限状态机（FSM）**：状态 + 转移条件。简单直观，但状态数随任务复杂度**平方增长**（N 个子任务的组合状态），且转移逻辑散在各处，复用困难。适合状态少的单流程（导航的 move/rotate/charge）。

**行为树（BT）**：把行为组织成一棵树，每个 tick 从根向下轮询：

- **Sequence**（顺序）：子节点全 SUCCESS 才 SUCCESS，否则 RUNNING/FAILURE——表达"先…再…最后…"；
- **Selector**（选择）：找到一个 SUCCESS 就停——表达"方案 A 不行就方案 B"；
- **Decorator**：重试、超时、取反等修饰；
- **Blackboard**：树内共享内存。

BT 的两大优势使它成为机器人编排的事实标准：**响应性**（每个 tick 都从根重扫，环境变化立即反映）和**模块化**（子树可复用、可独立测试）。

**LLM 规划**：让大模型把自然语言任务直接翻译成动作序列或 BT（SayCan 式"LLM 打分 + 技能库执行"、Code as Policies 等）。它解决的是**语义→任务**的映射，但输出的计划仍需确定性系统去执行与保障——"LLM 当大脑、BT 当小脑脑干"是当前的主流分工，11 篇会回到这个接口。

## 2. BT 与异步世界的相遇

BT 的 tick 语义天然假设"同步"：每个节点在被 tick 时要么立刻出结果，要么返回 RUNNING 下个 tick 再看。但机器人系统全是**异步服务**——MoveIt 规划是几秒的 action 调用、世界查询是跨进程的 service。于是产生 BT 工程的头号大坑：

> **在 async 回调里创建临时节点、同步等待结果 → 执行器（executor）死锁。**

## 3. 项目实例：M5.2 死锁与 AsyncTick 重构（本篇主角）

这是一个完整的"写错 → 定位 → 重构"故事，也是全系列工程价值最高的一篇实例。

**第一版**：BT 的 ROS2 插件在 async 回调里创建临时节点、同步等待服务结果——单臂时侥幸能跑，**双臂并发执行时 executor 死锁**（两个回调互相等待对方让出 executor）。

**重构方案（共享 Node + AsyncTick）**：

```
TaskPlanner ROS2 Node（唯一）
    └── BT Plugin
          └── async service/action client（共享 Node）
tick → 返回 RUNNING（future 未完成）
下个 tick → 检查 future → SUCCESS / FAILURE
```

即 BehaviorTree.CPP 的 `AsyncActionNode` 模式：**tick 永不阻塞，用 RUNNING 把"等待"显式化**。8 个插件全部重写为 async（AsyncMoveToNode、AsyncCheckSafetyNode、AsyncGraspNode、AsyncRecoverNode……）。

**四条关键发现**（AGENTS.md M5.2 原文摘要）：

1. BT XML 里 `{blackboard_key}` 引用不被底层节点构造解析——只能用扁平 Sequence 结构绕过；
2. Sequence/Selector 必须**记忆 RUNNING 子节点的位置**，否则 async 节点每次 tick 被反复重置——"从根重扫"的响应性优势和"异步断点续传"在这里正面冲突；
3. `wait_for_server()` 在 tick 内部会阻塞 executor——必须用非阻塞检查 + 重试；
4. **安全侧不对称**：服务不可用时，`AsyncQueryWorldNode` 返回 SUCCESS（世界查询失败就用默认值继续），`AsyncCheckSafetyNode` 返回 FAILURE（安全检查失败就**不许动**）。

第 4 条值得单独记住：同一个"服务挂了"，两个节点的正确答案相反——**fallback 方向必须由语义决定，不由工程便利决定**。

**演进注记**：这次重构还顺带完成了一次"mock → 真插件"的替换（`pick_place_ros2.xml` 成为默认，mock 插件降级为单元测试专用）。另外，任务协议也在同期从字符串 `"arm1:zone_a:ready"` 升级为 `TaskGoal.msg` 领域模型（M5.3），字符串解析保留做向后兼容——BT 的 goal 构造从此有了类型。**先跑通再升级，是整个 M5 的共同模式。**

## 4. LLM 在这个栈里的位置

项目对 LLM 的态度写在 M6.5 的命名决策里：Robot Runtime API 是**能力接口，"非自然语言，语言理解属 M7"**——即：编排层刻意不接 LLM，留了插槽。这个决策的合理性：编排层要的是**可验证的确定性**（BT 的每个分支可测试、可冻结），LLM 输出不可验证。正确的接口是 11 篇的 Skill 层——LLM 选技能，Skill Runtime 执行技能，precondition 检查兜底。

## 5. 边界与不足

BT 全部手写 XML（pick_place 是唯一成型的任务树），没有任务→BT 的自动编译；黑板机制因解析坑被迫绕开（扁平化），树的参数化能力打了折扣；没有"LLM 生成 BT"的任何实现——插槽留着但没插；双臂冲突场景（M5.6 Level 4 多任务调度）验证了优先级与抢占，但两个 BT 之间的资源竞争靠上层 Coordinator 仲裁，树本身对"别的树"无感知。

## 6. 一句话总结

> BT 赢在确定性与响应性，输在表达力——它不是被 LLM 取代的对象，而是 LLM 计划的"可验证执行层"。而它的第一个工程大坑（tick 不能阻塞）恰好出现在确定性与异步世界的接缝上。

下一篇讲贯穿一切的那条横切面：当速度限制、急停、碰撞保护需要"能推翻所有人"的权力时，安全应该住在哪里。
