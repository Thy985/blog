# 机器人的身体——自由度、URDF 与身体架构

> 大语言模型的"身体"是一张 GPU 和一块上下文窗口，机器人的身体是关节、连杆、传感器和执行器。理解具身智能，从理解"身体如何被描述"开始——因为一台机器人在软件世界里的一切存在，从一份 URDF 文件开始。

---

## 1. 自由度：身体的语法

**自由度（DOF, Degree of Freedom）**是机器人学的基本量词：一个刚体在三维空间有 6 个自由度（3 平移 + 3 旋转），一个关节提供一个或几个。两个基础规则：

- **任务空间 vs 关节空间**：把物体从 A 摆到 B 是任务空间的说法（6 DOF 位姿），机器人实际动的是关节空间（N 个关节角）。N ≥ 6 才可能任意定位末端；N > 6 是**冗余**——同一末端位姿有无穷多种关节构型，规划器反而有了选择的自由。
- **类型决定能力**。转动关节（revolute）、滑动关节（prismatic）、连续旋转（continuous）……关节类型决定控制方式：UR5e 的六个关节是位置控制的转动关节，Franka 是力矩控制，人形的"全身控制"（whole-body control）又是一套。**机器人之间的差异，首先不是外形差异，是控制接口差异**。

典型身体的自由度账本：一个 6 轴机械臂 6 DOF；加一个平行爪夹爪 1 DOF；一个可旋转躯干 +1；一个可俯仰头部 +1——这正是本项目的身体。

## 2. URDF：机器人的基因文件

**URDF（Unified Robot Description Format）**是一份 XML，用两种元素描述身体：

- `<link>`：刚体（连杆），带惯量、视觉外形、碰撞体；
- `<joint>`：连接两个 link 的关节，带类型、轴向、限位、父子关系。

整台机器人是一棵**从 base_link 长出来的运动学树**：每个 joint 定义子 link 相对父 link 的变换。这棵树同时服务三件事——仿真器按它做物理、规划器按它算运动学、可视化器按它画外形。**一份描述，三个消费者**，这就是为什么 URDF 是机器人的"基因"：改一个关节限位，仿真、规划、可视化同时变。

ROS 生态在这之上补了两层：

- **Xacro**：URDF 的宏语言——参数化、复用、算术。写一个 `ur5e_macro.xacro`，就能用不同前缀实例化多台相同的臂，避免复制粘贴五百行 XML。
- **SRDF**：语义补充——哪些 link 组成一个"规划组"（planning group）、哪些构型是"命名构型"（named states，如 home/ready）、哪些碰撞对可以被忽略（自碰撞矩阵）。

## 3. 传感器与执行器：身体的感觉与肌肉

**执行器**（肌肉）的关键参数是控制模式：位置控制简单可靠但"硬"（撞上障碍就硬顶），力矩控制柔顺但难稳（需要动力学模型和更高控制带宽），中间还有阻抗/导纳控制。夹爪通常独立于臂的控制（位置控制的开合 + 力阈值判断是否夹住）。

**传感器**（感觉）分两类：

- **本体感觉（proprioception）**：关节编码器（每个关节角）、IMU（姿态与加速度）——回答"我的身体在哪里"。硬件层最关键的本体感觉输出是**关节状态流**，本项目的频率是 500Hz（05 篇详述）。
- **外感受（exteroception）**：RGB 相机、深度相机、激光雷达、力传感器——回答"世界在哪里"。其中 RGB-D 相机一次给两路（颜色 + 深度），是 manipulation 的事实标准。

**传感器的布局是身体架构问题**：头部相机看得广但分辨率随距离衰减，腕部相机看得近且跟着手走（适合抓取末段的视觉伺服）——两者互补。传感器装在哪、挂哪个坐标系，决定了下游所有感知算法的设计空间。

## 4. 项目实例：一份 robot.yaml 与 16 个关节

项目在 URDF 之上又加了一层：**Robot Description Layer（M6.0）**——`robot.yaml` 用数据描述身体，`capability.yaml` 描述能力，代码生成器从 YAML 生成 URDF/SRDF/控制器配置。设计动机写在 AGENTS.md 里："机器人差异主要不是结构而是能力"。

`robot.yaml` 的骨架（简化）：

```yaml
robot:
  name: dual_ur5e_platform
  components:
    arms:
      - name: left_arm
        type: ur5e
        urdf: ur5e_macro.xacro      # 同一个宏，两个实例
        prefix: left_arm_
        controller: left_arm_joint_trajectory_controller
        workspace_bounds: [...]
    body:
      torso: { joint: torso_yaw_joint, axis: z, limits: [-3.14, 3.14] }
      head:  { joint: neck_pitch_joint, axis: y, limits: [-1.57, 1.57] }
```

M7.1 身体升级把双臂平台变成"人形上半身"：`base_link → torso_link（yaw）→ head_link（pitch）→ head_camera（RGB-D）`，外加躯干 IMU。升级后 ros2_control 管着 **16 个关节**（12 臂 + 2 夹爪 + 1 躯干 + 1 头）、7 个活跃控制器。两个设计细节值得注意：IMU 装在 torso_link 而不是 head_link（头部随颈部俯仰会污染姿态估计）；躯干和头是**独立控制器**（`torso_controller ≠ head_controller`），且 SRDF 里**刻意没有**全身规划组——"没有 arm1_full"，全身协调是留白而非遗留。

`capability.yaml` 把能力声明为数据，包括**负声明**：

```yaml
force_control:
  available: false
  reason: "UR5e simulation has no force control"
  conflicts_with: ["manipulation"]
```

机器人的能力边界和它的能力本身一样，是一等公民——这个声明在 12 篇会再次出现，它是全系列"诚实工程"的代表物。

## 5. 边界与不足

纯仿真身体：没有真实执行器——电机堵转、减速器背隙、连杆柔性这些真实身体的"脏物理"全部缺席，sim2real 差距从这里开始积累。夹爪物理未完整加载（Robotiq URDF 在 M6.2 标 ⬜，实际用模拟 attach/detach，见 10 篇）。`workspace_bounds` 目前是全旋转范围（`[-3.14, 3.14]` 全关节），没有做真实工作空间裁剪——即能力声明比物理事实宽松。

## 6. 一句话总结

> 身体是机器人的第一性约束：自由度决定能做什么，URDF 决定软件怎么理解它，传感器布局决定感知算法的设计空间，而能力声明必须包含"不能做什么"。
