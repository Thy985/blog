# 反代生态横向图景

> 把视角从"一个项目"拉到"整个生态"。
> 逆向反代类开源项目可以分成五类，每一类的难度、路线、可持续性都不同。
> 最反直觉的结论：客户端越开源，反代未必越容易。

---

## 1. 五类项目

围绕"把不提供公开 API 的 AI 服务逆向成 OpenAI 兼容接口"这一类项目，生态可以切成五层：

| 类 | 定义 | 典型 |
|---|---|---|
| **L1 单账号协议转换器** | 把一个账号的登录态转成 OpenAI 兼容 HTTP；无账号池、无调度 | 各类 `*2api` 单号版 |
| **L2 多账号治理网关** | 账号池 + 调度（轮转/权重/冷却/熔断）+ 面板 + 任务生态 | 本系列复盘的项目、通用网关 |
| **L3 商业化分发系统** | 计费、令牌售卖、多渠道、用户体系 | new-api / one-api |
| **D 类 网页版 AI 反代** | 反代 DeepSeek / 豆包 / ChatGPT 等网页版 | dsh-deepseek-web-login 等 |
| **F 类 编程 Agent 免费层反代** | 反代 OpenCode / Cline / Freebuff 等编程 Agent 免费层 | opencode2api 等 |

L1-L3 是"通用网关"的演进谱系，D 和 F 是按"上游形态"分的独立类。

## 2. D 类：网页版 AI 反代的四条路线

网页版 AI 反代（把 DeepSeek / 豆包 / ChatGPT 网页版包装成 API）按"谁发请求"分四条路线：

| 路线 | 谁发请求 | 浏览器是否常开 | 代表 |
|---|---|---|---|
| **A. DOM 自动化** | 页面自己 | 是 | Camoufox + Playwright |
| **B. 请求 Hook / 扩展** | 页面自己 | 是 | 浏览器扩展 |
| **C. 自建客户端（借浏览器环境）** | **程序自己** | 否（仅登录时） | dsh-deepseek-web-login |
| **D. 纯协议复刻** | 程序自己 | 否 | 早期手搓签名版 |

### 2.1 C 路线是演进方向

A/B 路线的痛点：**浏览器必须一直开着、改版选择器就废、资源占用大、并发受页面数限制**。

C 路线的关键洞察：**浏览器只在"登录"这一下出现，之后关掉窗口照常工作**。程序自己拼请求、自己解 PoW、自己解析 SSE——没有转发层，它就是客户端本身。

> **一个重要的概念澄清**：C 路线在严格意义上**不是反向代理**。反代是"客户端以为在跟源站说话，其实多跳了一跳"，而这类项目没有中间跳，它就是客户端。

### 2.2 豆包的 BrowserOnly：不逆向签名，逆向浏览器环境

一个更激进的变体：豆包前端的 `window.fetch` 已被服务端 JS 劫持，在浏览器内调 `fetch()` 时签名参数会被自动注入 URL query。

> **核心洞察：不逆向签名，逆向浏览器环境。** 于是"连签名都不用逆向"。代价是浏览器必须常开。

作者自述：传统纯协议复刻预计 2-3 天开发 + 持续维护；BrowserOnly 方式核心开发约 2 小时且**零签名维护成本**（服务端更新 JS 拦截器不影响）。

### 2.3 反爬对抗的三层战场

把所有网页版反代的对抗手段归类，是清晰的三层：

| 层 | 手段 | 成本 |
|---|---|---|
| **传输层**（TLS/HTTP2 指纹） | Node fetch 必被抓；Chromium 网络栈 cipher hash 与 Chrome 逐字节一致 | 走 Chromium 栈零新依赖 |
| **协议层**（签名 / PoW） | DeepSeek PoW 用官方 WASM 自解；豆包借 JS 自动注入签名 | 豆包最便宜 |
| **行为层**（节奏 / 会话 / 账号） | 固定值方差≈0 是最明确的机器特征；请求簇形状、会话卫生、上下文体量 | 全靠实测 |

> **结论**：如果只做一件事，做"走 Chromium 网络栈"——性价比最高。

## 3. 网页版 Tool 的真相与四种破解法

一个常见的疑问：**网页版 AI 定义好的 Tool，能不能接受外部引进的 Tools？**

**答：不能。这是网页版反代最硬的物理限制，且无解，只能"绕过"而不能"解决"。**

精确化成三层：

| 层 | 事实 |
|---|---|
| **协议层** | Web 端点根本没有 `tools` 字段，发了也没用 |
| **能力层** | 模型自己会不会用工具格式，取决于它见过什么 |
| **工程层** | 就算模型输出了，解析也是流式地狱 |

但"无原生 function calling"不等于"不能工具调用"。社区演化出**四种破解法**：

| 方法 | 原理 |
|---|---|
| ① 提示词协议 + 文本解析 | 把工具定义写进 system prompt，约定模型输出 JSON/XML 块，网关正则解析成 tool_calls |
| ② 借模型的 DSML 原生标记 | 某些模型自带工具调用标记，网关解析它 |
| ③ webTools 提示词 shim | 通用化的"提示词模拟层"，多 executor 共用 |
| ④ 上游自带工具白蹭 | 用网页版自带的联网搜索/文件上传等，不引入外部工具 |

> **打假**：看到"full tool calling support"要默认打问号——真正的判据是"能否在 agent 客户端（Codex / Claude Code）里跑通"，而不是 dashboard 里能返回一个 tool_calls 字段。几乎必然是 ①/③ 的模拟，而非原生。

## 4. F 类：编程 Agent 免费层反代

这是当下最卷的战场。上游是开源编程 Agent 的免费层（OpenCode Zen / Cline / Freebuff）。

### 4.1 OpenCode Zen 的五代风控编年史

这是最完整的样本——一个上游从"检查请求头"到"封死所有第三方"的五代升级：

```
第一代：检查请求头
  ├─ 规则：免费模型必须从官方客户端发起请求
  └─ 破解：请求头可从 GitHub 源码直接找到，容易伪造

第二代：动态计算的头
  ├─ 规则：x-request 和 x-session 由客户端本地计算，乱填不行
  └─ 破解：用 JS 脚本自动生成

第三代：检查请求 Body
  ├─ 规则：tools 数组里必须存在 name=bash 的项 + tools 数量 ≥ 2
  └─ 破解：塞入最小化的占位工具

第四代：TLS 握手指纹
  ├─ 规则：ClientHello 内容 / 密码套件协商方式 / 握手时序
  └─ 结果：成本急剧上升

第五代：直接封禁第三方
  └─ 持有有效 session + key 的第三方全部 403，只有真客户端能过
```

### 4.2 第三代是全报告最精彩的一处

> `tools` 数组里必须存在 `name=bash` 的项，**具体 schema 内容并不检查，可以最小化**；`tools` 数量必须 ≥ 2，第二个工具名任意。

**这说明上游的检测逻辑是"启发式形态匹配"而非"严格协议校验"**——它不验证你是不是真客户端，只验证"你的请求长得像不像"。

而社区的应对是一个**反馈循环**：被拒时把"观测到上游接受过的工具名"追加进去再重试——用反馈逆推服务端白名单。

### 4.3 反代的定位从"对抗"转向"隔离"

追着风控跑不可持续。博主的解法不是继续对抗，而是**把对抗隔离到一层网关里**：

```
旧思路：自己的应用 → 伪造客户端请求 → 上游
新思路：自己的应用 → [标准 API] → 反代网关 → 上游
                       （协议转换 / Key池 / 代理池）
```

> **核心洞见**：反代网关的真正价值不是"绕过"，而是**把"上游多变性"吸收进一层可替换的适配器**。客户端只跟稳定的 OpenAI 协议说话，上游怎么变都不影响它。

## 5. 两层 Harness：把"网页 Agent 的模型"抽出来

一个独特视角：**网页版 Agent 反代 = 两层 Harness**。

网页版 Agent 本身就有完整的 agent 运行环境。如果你反代它的请求塞进 Codex / Claude Code，相当于外层 harness（网页 Agent）+ 内层 harness（你的 coding agent）。

### 5.1 两种截然不同的形态

**形态一：把网页 Agent 的"模型"抽出来（去 harness）**

代理整个任务 / 会话端点，把事件流（plan step / tool call / artifact）翻译成 OpenAI 的 chunk 流。

**形态二：承认两层 Harness，把外层当"规划器"**

```
你打一行字
  → 网页 ChatGPT（云端）负责"想"：规划、拆需求、派活
      → MCP connector → 隧道 → MCP 桥（本地）
          → run_codex / run_claude_code / read_file / write_file
              → Claude Code 真改文件；Codex 做执行/审查
  → 结果原路返回
```

三个角色分工：ChatGPT = 项目经理｜Claude Code = 干活的工程师｜Codex = 审查的同事。人肉中转被自动化。

### 5.2 两层 Harness 的工程后果

| 后果 | 机理 |
|---|---|
| 上下文双层膨胀 | 外层 + 内层的 system prompt 与工具目录叠加，每轮全量发送 |
| 工具协议双重复刻 | 外层用提示词模拟工具，内层自己也有工具协议，模型在两套格式间切换 |
| 审批链断裂 | 内层 harness 的审批机制被外层绕过 |
| 限流归因困难 | 撞限流时不知道是外层的量还是内层的量 |
| 封号判定更严 | "同人多号" + "机器行为" 两个信号叠加 |

## 6. 一个反直觉的核心结论

把五类合起来看，最反直觉的结论是：

> **客户端越开源，反代未必越容易——因为上游会把力气全花在服务端门禁上。**

| 上游 | 客户端源码 | 服务端门禁 | 反代可持续性 |
|---|---|---|---|
| 闭源 + 轻门禁（如本系列项目） | 闭源 | 轻 | **高**（协议稳，逆一次永久受用） |
| 开源 + 激进门禁（如 OpenCode Zen） | 完全开源 | 重且快速迭代 | **低**（上游已公开承认封第三方） |
| 开源 + 官方 API 化（如 Cline） | 开源 | 提供官方 API | 高（退化成 Key 聚合） |

**开源客户端 + 想守住免费层的上游 = 最不适合反代的组合。** OpenCode Zen 就是典型——客户端代码全公开（请求头直接从 GitHub 读），但服务端五代升级，最后直接 403 所有第三方。

## 7. 多账号策略截然相反

另一个反直觉的发现：**多账号策略不是"越先进越好"，而是由上游的计费/风控模型决定**。

| | 按账号计费的上游 | 免费额度 + 严格风控的上游 |
|---|---|---|
| 目标 | **把流量分散到多号**（避免单号超限） | **把流量聚在单号**（避免"同人多号"判定） |
| 手段 | 加权轮盘 + 熔断 + 会话粘性 | 账号库 + 手动切换 + 拒绝自动轮换 |
| 理由 | 按账号计积分，分散可扩容 | 免费额度 + 风控把多号关联判为更严重的滥用 |

> **借鉴任何项目前，先判断"上游的约束模型是否相同"**。两条路线的技术手段看似相反，实则都正确。

## 8. 小结

横向看完整个生态，本系列复盘的那个项目（闭源客户端 + 轻门禁 + 按账号计费）恰好落在**甜区**里。下一篇总结方法论与选型——**选上游与长期工程**。
