# 上游逆向：抓包与认证

> 协议层的第一步：把客户端的网络行为扒清楚——域名分工、认证流程、请求头体系。
> 每一步后面都跟着"客户端不会告诉你的隐含约束"。

---

## 1. 抓包：三域分流

一个产品客户端的网络行为往往**分布在多个域名**上。不把域名分工理清，会把请求发错地方然后一脸懵。

典型分工（以一个有 CLI + 桌面 + Web 三端的 AI 编程助手为例）：

```
主 API 域    → 聊天补全、token 刷新、OAuth、模型列表、成长任务域
业务域 A     → 每日签到、余额查询、活跃上报
业务域 B     → 任务领奖（Web 域，非 CLI 域）
```

**三个域名都返回 JSON，但用途完全不同。** 初期把签到请求发到主 API 域，上游会返回 400——因为领奖必须走 Web 域。

### 1.1 WAF 路径避让

主 API 域上往往有多个 chat 路径（如 `/console` 和 `/v2`），但**只有一个是干净的**：

- `/console` 挂了上游云的 WAF body 内容规则——`printf` / `whoami` 等命令执行特征会**确定性 403**
- `/v2` 是干净端点，实测等价

> **教训**：同一个上游的"等价端点"未必都可用。选错路径，命令执行类 prompt 会触发风控 403，而且表现形式是"部分请求正常、部分请求 403"，极难定位。

## 2. OAuth 设备流

这类产品的登录**不是 API Key，而是 OAuth 2.0 device flow**：

```
POST /auth/state?platform=CLI
  → 拿 device_code + 授权 URL（用户在浏览器完成登录）

POST /auth/token?state=<device_code>
  → 轮询取访问令牌 + 刷新令牌

POST /login/account?state=<device_code>
  → 取账号信息（uid、enterpriseId、nickname）

POST /auth/token/refresh
  → 刷新 token（永不携带 X-Refresh-Token 头，该头只在刷新请求出现）
```

### 2.1 设备风控 token 的三层 fallback

`X-Device-Token` 是设备风控 token，来源有优先级：

```
auth 运行时持有 > 配置文件写死的 device_token > 配置文件指向的 device_token_file
```

> **设计含义**：这条优先级链是为了"运行时 > 配置 > 文件"的渐进式兜底。运行时拿不到才读配置，配置没有才读文件。多数情况走运行时，保证 token 新鲜。

## 3. 请求头体系

出站请求不是裸 HTTP，有一套完整签名：

```
User-Agent: CLI/<ver> <Product>/<ver>      (可配置覆盖)
X-<Product>-Request: <签名>
X-Device-Token: <设备风控 token>
X-IDE-Version: <客户端版本>
X-Product: SaaS
X-User-Id: <账号 uid>
X-Forwarded-For: <客户端 IP>               (可选)
```

### 3.1 三个逆向出的约束

**约束 1：UA 不能写死**

`CLI/2.63.2 Product/2.63.2` 是现状，但必须可配置覆盖。原因：官网"使用端"列表按**出站 UA 服务端归因**——想显示不同的产品名就得配不同的 UA。写死就失去了归因控制。

**约束 2：X-Refresh-Token 永不携带**

这个头**只出现在 token 刷新请求**。早期版本在所有请求里都带这个头，触发了上游风控。

> **教训**：请求头不是"越多越好"。某些头是特定请求专用的，乱带会触发风控。

**约束 3：X-Product / X-IDE-* 有后向兼容**

`X-Product="SaaS"` 和是否设 `X-IDE-*` 取决于 `ClientName` 是否为空。**突变归因**会把历史用量统计打乱——所以这些头不能随意改，改了上游就把你的用量统计归到一个新"产品"下。

## 4. token 刷新的三个坑（行为层）

OAuth device flow 本身是标准协议，但**token 刷新**有三个隐藏的并发/数据陷阱。这是行为层的内容，但放在这里讲，因为它是"认证"的一部分：

### 坑 1：并发刷新的后写覆盖

两个刷新请求同时发出，后写覆盖先写。**实测服务端无 rotation 撤销**——两个新 token 都有效。

必须加**写回守卫**（AND 语义）：锁外期间若另一刷新已完成，则两 token 必同时变化。没有这个守卫，高并发下 token 会被覆盖成旧值。

### 坑 2：持锁 I/O

早期版本在锁内执行 HTTP 请求，上游 hang 时 120 秒独占互斥锁，阻塞同账号的原子写和其他刷新。

**修法**：锁外执行 + 30 秒 context 超时。锁只保护内存状态，不保护网络 I/O。

> **教训**：互斥锁保护的应该是**临界区的内存状态**，绝不该保护网络 I/O。网络 I/O 的不确定性会传染给锁，放大故障半径。

### 坑 3：ExpiresAt 不可信

实测 token 刷新响应**恒带 `expiresIn=5184000`（60 天）**，但 JWT 内部 `exp - iat` 与 `expiresIn` 严格自洽。超过 10 年的 `expiresIn` 要按脏数据处理，**不写 ExpiresAt**——防止"是否需要刷新"判断永远为假，导致 token 永不刷新反而真过期。

> **教训**：服务端返回的字段未必可信。字段值异常时，宁可相信 token 内部的自洽数据（JWT 的 exp/iat），也不要盲信外层字段。

## 5. 小结

上游逆向的协议层产出一张清单：

| 项 | 内容 |
|---|---|
| 域名分工 | 主 API 域 / 业务域 A / 业务域 B，领奖必须走 Web 域 |
| 认证 | OAuth device flow，device_code 轮询取 token |
| 请求头 | UA 可配、X-Refresh-Token 隔离、X-Product 归因 |
| token 刷新 | 并发写回守卫、锁外 I/O、ExpiresAt 不可信 |

但这只是协议层。下一篇进入更密集的坑——**请求体改写的 12 步**：每个字段都有实测 case。
