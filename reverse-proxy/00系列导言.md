# 系列导言：从逆向到一个可用的反向代理网关

> 这一系列记录我对一个「把闭源 AI 编程助手的私有 API 逆向成 OpenAI 兼容网关」项目的完整复盘。
> 真正值得写的不是最终那个网关能跑，而是**这一整条逆向工程方法论**：协议层怎么扒、语义层怎么学、行为层怎么猜、二进制怎么读、账号池怎么调度、上游该怎么选。

---

## 1. 为什么写这个系列

现在社区存在大量反向代理出Token的开源项目和技术，对我们来说真的是眼花缭乱。现在以 https://github.com/Sliverkiss/workbuddy2api这个开源项目为例，我把其中最核心的技术知识点提炼、去敏感化、重写成一个 9 篇的博文系列——目标是让一个不熟悉这个具体项目的人，读完也能：

1. 理解「把一个没有公开 API 的产品做成 OpenAI 兼容网关」到底要经历什么
2. 掌握协议层 / 语义层 / 行为层三层的逆向框架
3. 学会读 Go 二进制的实战流程（Ghidra + 侦察）
4. 理解账号池、冷却、错误分类、选号这些网关核心机制的**为什么**
5. 能在面对一个「要不要反代某个上游」的决策时，用风控对抗成本的视角做判断

## 2. 这个系列在讲什么

一句话：**在一个闭源产品没有公开 API、错误码语义全靠实测、二进制行为需要反编译验证的条件下，完成「协议逆向 → 网关实现 → 账号资产经营 → 生态定位」的完整闭环。**

主题脉络：

```
逆向三层模型（协议/语义/行为）
  ↓
上游逆向（抓包 → OAuth → 请求头 → 请求体改写）
  ↓
错误分类 14 路决策树（状态码 + 关键词双层判定）
  ↓
冷却与账号池（三种冷却 / 模型级豁免 / 加权选号 / 会话粘性）
  ↓
本体逆向（Ghidra 读 Go 二进制，验证与补全源码）
  ↓
反代生态横向图景（五类项目 / 两条技术路线 / 两层 Harness）
  ↓
方法论与选型（检查清单 / 工具链 / 成本 / 上游选择）
```

## 3. 真正的价值藏在哪

真正值得写的是这些**反直觉的经验**：

1. **协议层最简单，行为层最难。** 这个项目的壁垒不在协议（12 步 JSON 改写），而在语义（错误码）和行为（并发刷新陷阱、指纹体系、token 管理）。

2. **错误分类顺序 > 分类准确性。** 14 路决策树的每一步「先于谁」都有实测 case 支撑。顺序错了会白扔一个账号 12 小时——比分类错了更致命。

3. **上游返回 429 不是简单"等等再试"。** 429 有至少三种冷却语义，其中一种要解析 body 里的「将在某时刻重置」并**按 UTC+8 解释**。

4. **反代网关的真正价值不是"绕过"，而是"把上游多变性吸收进一层可替换的适配器"。** 客户端只跟稳定的 OpenAI 协议说话，上游怎么变都不影响它。

5. **客户端越开源，反代未必越容易。** 开源客户端让上游把全部力气花在服务端门禁上——有项目经历五代风控升级，最后上游直接封死所有第三方。

6. **选上游时，风控对抗成本是一等指标。** 闭源客户端 + 轻门禁 + 协议稳定 = 甜区；开源客户端 + 激进门禁 = 最差组合。
