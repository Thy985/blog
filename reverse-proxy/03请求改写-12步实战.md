# 请求改写：12 步实战

> 客户端发的是标准 OpenAI 请求，上游要的是私有格式。12 步 JSON 改写全部从客户端流量中逆向出来。
> 这是整个项目里坑最密集的一层——每一步都有"换号无用，只能发送前修"的实测 case。

---

## 1. 为什么要改写

标准 OpenAI 客户端发 `/v1/chat/completions`，请求体是标准 OpenAI 格式。但上游 `/v2/chat/completions` 接受的请求体**不是标准 OpenAI**——它有一套自己的字段名、枚举值、约束。

不改写会怎样？**400**，附带一个业务错误码。而这些改写点**没有一个写在文档里**，全部是从客户端流量里逐字段对比抓出来的。

12 步改写的清单：

```
 1. 强制 stream:true                  → 上游拒绝非流式
 2. max_completion_tokens → max_tokens → OpenAI 新别名，上游不认
 3. clampGPTMinMaxTokens              → GPT 系 max_tokens < 16 确定性 400
 4. stream_options 补 include_usage   → 上游据此在末帧返回 usage
 5. normalizeToolChoice               → 对象 → 字符串；"none" 删 tools+functions
 6. normalizeToolPatterns             → `\_` → `_`（正则转义修复）
 7. normalizeRoles                     → developer → system（上游 role 白名单）
 8. normalizeImageURL                  → 字符串 → 对象形态
 9. mergeAdjacentToolCalls            → 背靠背 tool_calls 合并
10. repackToolResultBlocks            → 非 tool 消息挪后
11. cleanupOrphanToolCalls            → 删孤儿 tool 调用
12. injectThinking + backfillReasoning → 思维链注入
```

下面挑几个最精彩的实测 case 讲。

## 2. 第 3 步：GPT max_tokens 下限

**背景**：上游 GPT 系（多个 GPT 模型）对 `max_tokens < 16` 一律返回 400，错误码 `11133`。

15 拒、16 过，同账号同 body 对照。

**触发场景**：某编程 Agent 切换模型时发 `max_tokens` 极小的探针。全号轮转同样被拒 → 客户端 503，模型永远切不过去。

> **根因判断**：账号与 body 其余部分无关，**换号无用，只能在发送前修**。

**修法**：发送前 clamp 到 16（GPT 系）。这是"协议层改写"的典型——问题是协议层面的（请求体字段值），解法也是协议层面的（发送前改）。

## 3. 第 6 步：`\_` 正则转义

**实案**：某个插件的工具 `runId` / `previousRunId` 字段名带 `^agent\_run\_`，上游全家确定性 400 → 网关侧归为"客户端错误"只换号不罚 → 轮转烧满 5 连败触发连败降权 → 客户端 503。

**根因**：上游对 `tools[].function.parameters` 做**严格 JSON Schema / 正则文法校验**，`\_` 不是任何正则文法的合法转义。所有主流引擎（RE2 / PCRE / JS Annex B）都宽容地视为 `_` 本身——**上游校验器比它们全部更严**。

**修法**：`normalizeToolPatterns` 在发送前递归改写 `\_` → `_`。归一无损（各引擎实测 + 上游对照探针：归一后 200）。

> **教训**：上游的校验严格度可能超过所有主流引擎的共识。一个"看起来无害"的转义字符，能引发一连串"换号 → 连败 → 降权 → 503"的级联故障。

## 4. 第 7 步：developer 角色归一化

上游对 messages 的 `role` 字段做**白名单校验**，`developer` 不在白名单内，命中即 400，错误码 `11128`。

`developer` 是 OpenAI 新规范里 `system` 的别名（新客户端用它承载 system 级指令），改写为 `system` 不丢语义。

> **注意两个边界**：
> 1. **只认 `developer` 这一个值**，其余 role 一律原样保留。不要扩面改其他 role。
> 2. **不合并多 system**——上游对多 system 的行为尚未实测，合并会引入新变量。

## 5. 第 9-11 步：tool call 配对断裂

不完整配对的 `tool_calls` / `tool` 结果会让上游对之后每条消息都返 400。

**修法三步，顺序不能换**：

1. `mergeAdjacentToolCalls`——最先跑，把背靠背的两条 `assistant.tool_calls` 合成一条
2. `repackToolResultBlocks`——插在结果中间的非 tool 消息挪后
3. `cleanupOrphanToolCalls`——删孤儿

> **教训**：多步改写的**顺序**是协议的一部分。先合并、再重排、最后删孤儿——顺序反了会制造新的断裂。

## 6. 第 5 步：tool_choice 归一化

上游的 `tool_choice` 是 `string` 类型，但 OpenAI 发的是对象。不改就 400，错误码 `11101`。

更坑的是 `"none"` 的处理：删 `tool_choice` + 删 `tools` + 删 `functions`。**只删 `tool_choice` 不删 `tools`，上游照样报错**。

> **教训**：一个"删除"操作可能是**级联删除**。只删目标字段不够，要把它关联的字段一起删，否则上游仍按"有 tool 定义但选择不用"处理，照样报错。

## 7. 协议层改写的共性

把这 12 步合起来看，能提炼出协议层改写的几个共性：

### 7.1 每一步都是"换号无用"的请求级问题

12 步里没有一个能靠"换账号"解决——它们都是**请求体本身**的问题。所以全部归为"请求级错误"，在发送前归一化，不轮转、不罚号、不冷却。

### 7.2 改写顺序是协议的一部分

12 步有严格的执行顺序。顺序错了会制造新的问题（如 tool call 配对断裂的三步）。

### 7.3 上游校验可能比主流引擎更严

`\_` 转义这种"所有引擎都宽容"的东西，上游可能严格拒绝。逆向时不能假设"主流引擎接受的，上游也接受"。

### 7.4 字段名差异、枚举值差异、必填项差异都要实测

`max_completion_tokens` vs `max_tokens`、`tool_choice` 对象 vs 字符串、`image_url` 字符串 vs 对象——这些差异没有一个写在文档里，全部从客户端流量逐字段对比抓出来。

## 8. 一个元层面的观察

12 步改写最反直觉的一点：**协议层的"复杂性"不来自协议本身，来自"标准协议与私有协议的摩擦"**。

如果上游就是标准 OpenAI，12 步一步都不需要。正是因为上游在标准基础上做了"自己的私有约定"（强制流式、字段名别名、role 白名单、正则严格校验），才需要这么多改写。

> **这给"做网关"一个启示**：改写层的本质是**协议翻译器**。它的复杂度等于"标准协议"与"私有协议"的差异面积。差异越大，改写层越厚——但这个厚度是**可替换的**：换一个上游，只换这层，客户端侧的稳定协议不变。
