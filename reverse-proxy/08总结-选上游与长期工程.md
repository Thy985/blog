# 总结：选上游与长期工程

> 把整个系列的零散经验，沉淀成可复用的方法论：一份检查清单、一套工具链、一个成本模型、一个选上游的判断框架。

---

## 1. 上游逆向检查清单

如果你要从零做一个反代网关，完整的检查清单：

```
□ 抓包：客户端运行时的所有 HTTP 请求
□ 归类：按域名/路径分组，标出每个端点的用途
□ 认证：OAuth 设备流 / API Key / 签名算法
□ 请求头：UA、自定义头、签名、设备 token
  □ 哪些头是"特定请求专用"（如 X-Refresh-Token 只在刷新出现）
  □ 哪些头会触发风控
  □ UA 可配置化（不能写死，影响归因）
□ 请求体：字段名差异、枚举值、必填项
  □ 别名字段（如 max_completion_tokens → max_tokens）
  □ 字段类型差异（如对象 → 字符串）
  □ role 白名单（如 developer → system）
  □ 正则转义严格度（可能比主流引擎更严）
□ 响应体：SSE 格式、usage 字段、错误码体系
□ 错试：每个错误码的含义和处置策略（需要真实账号试）
  □ 错误码语义
  □ 分类顺序（顺序 > 准确性）
  □ 关键词名单（宁缺毋滥）
□ 限流：429 body 文案格式、重置时间解析
  □ 重置时刻按时区解释
  □ 三种冷却语义（带重置 / 不带 / 固定短冷）
  □ 模型级限流豁免
□ 冷却：每种错误类型的冷却时长和策略
□ 账号治理：选号算法、会话粘性、积分保底
□ 任务生态：签到 / 保活 / 任务体系（如有）
```

## 3. 成本模型

| 成本项 | 说明 |
|---|---|
| 时间 | 上游逆向：数周到数月（取决于 API 复杂度） |
| 账号 | 错误码语义需要真实账号触发，可能消耗配额 |
| 工具 | Ghidra 免费，IDA 需授权 |
| 代码量 | 一个完整 Go 反代网关约 50KB 源码，核心逻辑集中在 5 个文件 |
| 维护 | 上游持续迭代时，需要定期同步适配（每次同步可能引入不兼容） |

## 4. 选上游：风控对抗成本是一等指标

整个系列最重要的元结论：**选上游时，风控对抗成本是一等指标，比任何技术能力都重要。**

### 4.1 甜区判断

值得反代的上游，要同时满足：

| 维度 | 甜区 | 最差组合 |
|---|---|---|
| 客户端 | **闭源**（逆一次二进制，永久受用） | 开源（上游把力气全花服务端门禁） |
| 服务端门禁 | **轻**（静态化即可绕过） | 激进且快速迭代（追着跑） |
| 协议稳定性 | **稳**（上游不再频繁改协议） | 频繁变（每次都要适配） |
| 计费模型 | **按账号计费**（分散流量可扩容） | 免费额度 + 严格风控（聚拢流量） |

### 4.2 一个反直觉的"护城河"

一个上游删库 / 停止维护，看起来是风险，但从风控对抗角度**反而是护城河**：

- 上游不再更新 → 协议冻结 → **一次性逆尽的成本换来永久稳定**
- 没有服务端门禁迭代 → 不需要"追着风控跑"

> **对比**：OpenCode Zen 上游持续迭代风控，社区投入七个独立 PR 才勉强维持可用，最后上游直接公开承认"只有真客户端能过"——七个 PR 的适配成本换不来可用性。

### 4.3 不值得反代的情况

| 情况 | 为什么不值得 |
|---|---|
| 上游已提供完整官方 API | "反代"退化成"Key 聚合"，没有逆向价值 |
| 上游客户端开源 + 服务端激进门禁 | 追着跑不可持续，上游最终会封死第三方 |
| 上游明确反对第三方接入 | 法律与伦理风险，且技术上也守不住 |

## 5. 反代网关的真正价值

把整个系列的经验合起来，反代网关的真正价值不是"绕过"，而是：

> **把上游多变性吸收进一层可替换的适配器。**

```
客户端（OpenAI 兼容）  ← 稳定，不变
       │
  ┌────┴────┐
  │  网关   │  ← 协议改写 / 错误分类 / 账号治理 / 面板
  └────┬────┘
       │
    上游私有 API  ← 多变，会迭代
```

- 上游协议变更 → 只影响网关的"上游适配层"一层
- 客户端侧的 OpenAI 协议、账号池治理、面板全部稳定
- 换一个上游 → 只换适配层，其余复用

这是反代网关存在的结构性理由——**它把"上游的不可控"隔离在一个可替换的边界内**。

## 6. 一条贯穿全系列的主线

回头看整个系列，有一条主线：

> **协议是公开的，行为模型不是。**

- **协议层**（请求改写）——能转发的门槛，12 步 JSON 改写
- **语义层**（错误分类）——会处理错误的门槛，14 路决策树
- **行为层**（账号治理）——能长期运营的门槛，账号池、冷却、指纹、token 管理

一个网关的成熟度，取决于它在这三层各走多深。

> 真正难的部分（账号资产经营）需要长期运营真实账号才写得出来；真正麻烦的部分（反爬 + 工具伪造）取决于上游选择——**选对上游，就避开了最麻烦的那一层**。

## 7. 系列结语

这个系列复盘的，表面上是"怎么逆向一个闭源 AI 编程助手做成网关"，实质上是：

1. **逆向工程的三层方法论**——协议 / 语义 / 行为
2. **一个完整网关的七层结构**——抓包 → 认证 → 改写 → 分类 → 冷却 → 调度 → 本体验证
3. **整个反代生态的五类图景**——单号 / 治理 / 分发 / 网页版 / 编程 Agent
4. **一个选上游的判断框架**——风控对抗成本是一等指标

这些是可迁移的。无论你面对的是哪个上游，这套框架都适用——只要你愿意花时间把它的协议层、语义层、行为层各走一遍。

> **真实项目中最有价值的部分，往往不是配方，而是那些失败、反转和停止信号。** 这与天气分类系列的经验，竟是相通的。
