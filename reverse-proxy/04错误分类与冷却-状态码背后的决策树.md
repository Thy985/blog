# 错误分类与冷却：状态码背后的决策树

> 上游返回的错误不是标准 OpenAI 格式，而是一套自己的业务码体系。每个 code 对应不同的处置策略。
> 分类错了就是白扔号或冤枉好号——而分类顺序错了，比分类错了更致命。

---

## 1. 为什么需要错误分类

上游返回的错误不是标准 HTTP 状态码，有一套**自己的业务码体系**。每个 code 对应不同的处置策略：

- 有的错误是**账号问题**（余额耗尽、会话失效）→ 冷却账号
- 有的错误是**请求问题**（请求体解析失败）→ 不罚号，换号也没用
- 有的错误是**可自愈的**（限流）→ 短冷却自愈
- 有的错误是**永久性的**（积分耗尽）→ 硬冷却到第二天

分类错了就是白扔号或冤枉好号。

## 2. 14 路决策树

完整的错误分类是一个**多层判定链**：从状态码 + body 关键词双层判定。整体形态：

```
上游 HTTP 响应 (status + body)
    │
    ├─ ① 模型被屏蔽 → 模型级错误
    │    只认 400/404
    │
    ├─ ② status==402 → 硬额度耗尽
    │    真正的计费余额耗尽，最严最先判
    │
    ├─ ③ body 含 sessionDead 关键词 → 会话失效
    │    ["Offline user session not found", "12153"]
    │
    ├─ ④ body 含 accountFault 关键词 → 账号异常
    │    ["request illegal", "trial not activated", ...]
    │
    ├─ ⑤ status==429 + code 14018 → 硬额度耗尽
    │    明确的积分耗尽，必须先于通用 429 兜底
    │
    ├─ ⑥ status==429 → 软限流
    │    限流状态码兜底，先于硬关键词（避免误归硬冷却白扔号 12h）
    │
    ├─ ⑦ body 含 hardCredit 关键词 → 硬额度耗尽
    │    ["insufficient credit", "quota exceeded", "积分不足", ...]
    │
    ├─ ⑧ body 含 softRate 关键词 → 软限流
    │    ["rate limit", "too many requests", "限流", ...]
    │
    ├─ ⑨ prompt 超长 → 请求级语义最具体，须先于 404 兜底
    │
    ├─ ⑩ status==404 → 未找到
    │
    ├─ ⑪ status>=500 → 服务端错误
    │
    ├─ ⑫ WAF 拦截 → 403 且无业务信封，判在通用 4xx 兜底之前
    │
    ├─ ⑬ status==400 + code 11135 → 图片无效
    │
    ├─ ⑭ 内容拦截 → 误报信号，不罚账号
    │
    ├─ ⑮ 参数错误 → 不冷却、不熔断、不计错、不轮转
    │
    └─ ⑯ 兜底 → 客户端错误 / 未识别
```

## 3. 分类顺序 > 分类准确性

这是全章最核心的一句话。**14 路的顺序不是随意排的——每一步的"先于谁"都有实测 case 支撑**：

| 顺序约束 | 原因 |
|---|---|
| 模型不存在先于 4xx 兜底 | 不先判 → 坏号留在池内反复被选中 |
| 14018 先于 429 | 不先判 → 误判为可自愈软限流，全池冷却时反复兜底 |
| 429 先于 hardCredit 关键词 | 不先判 → 限流被误归硬冷却，白扔号约 12 小时 |
| prompt 超长先于 404 | 不先判 → 404 兜底误归"未找到"，只冷却不透传 |
| 会话失效先于 429 | 不先判 → 混合文案的响应会被错误归类 |
| WAF 403 先于 4xx 兜底 | 不先判 → 连环 403（只换号不罚的根因） |

### 3.1 三个最典型的顺序坑

**坑 1：429 状态码必须先于硬关键词**

429 的 body 高频携带 `"quota exceeded"` / `"额度不足"` 等**跨计费 / 限流两界**的措辞。如果先做关键词匹配（hardCredit 先判），会把限流误归为"积分耗尽"硬冷却到第二天，白扔号约 12 小时。

> **状态码是比关键词更权威的信号**：上游既然给了 429，就按限流语义处理。宁可短冷却自愈，不可长冷却弃号。

**坑 2：14018 必须先于通用 429**

14018 是明确的积分耗尽业务码。它必须先于通用 429 兜底，否则会被误判为可自愈的软限流，在全池冷却时反复兜底选中——每个请求都打在这个已经死掉的号上。

**坑 3：WAF 403 必须先于 4xx 兜底**

带业务信封的 403 已被上方各层捕获，走不到通用 4xx 兜底。但**空体 / HTML 的 403**（WAF 拦截）永远不会命中那些带文案的关键词——如果先做 4xx 兜底，会把 WAF 拦截归为"客户端错误"，只换号不罚，导致**连环 403**。

## 4. 关键词名单："宁缺毋滥"原则

错误分类用**关键词子串匹配**，名单全部从上游二进制的只读数据段提取（不是编的，是上游返回过的所有错误文案的汇总）：

| 名单 | 条目 | 来源 |
|---|---|---|
| 会话失效 | 2 | 实测：会话失效的两种文案 |
| 账号异常 | 3 | 实测：账号异常的三种文案 |
| 硬额度 | 16 | 实测：积分耗尽的 16 种中英文措辞 |
| 软限流 | 8 | 实测：限流的 8 种中英文措辞 |
| prompt 超长 | 4 | 实测：上下文超限的 4 种形态 |
| 内容拦截 | 3 | 实测：内容策略拦截的 3 种文案 |
| 图片无效 | 3 | 实测：图片错误的 3 种文案 |

**名单的"宁缺毋滥"**：只收录**明确指向某一类错误**的措辞。不收无关 code（如"今天已签到"这类业务提示），避免误判。

> **原则**：关键词是子串匹配，收得越宽，误判越多。宁可漏掉一个罕见文案（落到兜底分类），也不要收进一个会误伤健康账号的宽词。

## 5. 冷却语义：429 不是"等等再试"

错误分类决定了处置策略，而处置策略的核心是**冷却**。上游的 429 不是简单的"等等再试"，有至少三种冷却语义：

```
429 + body 含「将在 YYYY-MM-DD HH:MM:SS UTC+8 重置」
  → 冷却到那个墙钟时刻（按 UTC+8 解释），封顶 2 小时
  → 注意：此前只认中文文案 → 其他语言的 body 解析不到 → 退避基数反复翻倍

429 + 无重置文案
  → 600 秒起指数退避，封顶 2 小时
  → 连续触发退避，不能重置

404 → 固定 60 秒短冷却
402 → 硬冷却到次日 04:00
会话失效连续 3 次 → 永久禁用
```

### 5.1 一个时区陷阱

429 的 body 里那句「将在 YYYY-MM-DD HH:MM:SS 重置」要**按 UTC+8 解释**。

> **教训**：冷却解析的坑不在"要不要冷却"，在"按什么时区解释重置时刻"。此前只认中文文案时，其他语言的 body 解析不到重置时刻，只能退避——退避基数反复翻倍，冷却时间失控。

### 5.2 模型级限流豁免

**不是账号整体被限流**——账号健康，只是这个**模型**此刻被限。

- 冷却由模型级限流触发时会记录触发模型
- 同一账号改用**其他模型**请求时视为可用
- 同模型或未记录模型的冷却回到现状

**为什么重要**：如果没有模型级豁免，一个模型被限 → 整个账号冷却 → 其他模型也跟着不能用 → **池子越来越小**。

### 5.3 会话失效阈值

单次会话失效**不禁用**，连续 3 次才禁用。

- 太宽松 → 坏号反复被选
- 太严格 → 偶发网络抖动误杀好号

## 6. 一句话总结

> **状态码是权威信号，关键词是补充信号，分类顺序是生死线。**

一个网关能否长期运营，不取决于它能转发多少流量，取决于它对上游错误的理解深度——哪些错误该冷却、哪些该换号、哪些该透传、哪些连号都不用换。下一篇进入账号治理的核心——**账号池调度**。
