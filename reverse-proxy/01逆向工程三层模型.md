# 逆向工程三层模型

> 协议层最简单，行为层最难。一个逆向反代项目的壁垒不在协议，在语义和行为。

---

## 1. 逆向工程的目标：不是"破解"，是"理解"

逆向一个闭源产品的网络行为，通常不是为了绕过授权，而是为了：

> **理解一个没有公开 API 文档的商业产品的网络行为，然后写一个网关把它包装成标准协议。**

典型场景：

- 一个产品有桌面 CLI 客户端，但**没有公开 API 文档**
- 它的 API 路径、请求头、错误码、限流语义**全在客户端二进制里**
- 你想做一个 OpenAI 兼容网关，就得把客户端的行为扒清楚

## 2. 三个层次

逆向工程不是一件事，是三个层次的问题。每一层的**难度、方法、产出**都不同：

| 层次 | 问题 | 方法 | 产出 |
|---|---|---|---|
| **协议层** | API 长什么样？路径、参数、返回格式？ | 抓包 | 端点清单、请求/响应 schema |
| **语义层** | 错误码什么意思？限流后等多久？ | 实测 + 分类 | 错误决策树、冷却策略 |
| **行为层** | 客户端为什么这么做？有什么隐含约束？ | 二进制分析 + 实测 | 指纹体系、token 管理、并发陷阱 |

### 2.1 协议层：最简单

协议层只回答"API 长什么样"——路径、参数、返回格式。这部分**抓包就能拿到**，是最低级的逆向。

但协议层有个隐蔽的复杂性：**请求体格式未必是标准协议**。你给上游发的是标准 OpenAI 请求，上游要的可能完全是另一套字段。这种差异只能逐字段对比抓出来。

### 2.2 语义层：需要真实账号

语义层回答"错误码什么意思、限流后等多久"。这部分**没法纯靠抓包**——你必须拿真实账号去触发每个错误，然后归类成决策树。

语义层的产物是一个**错误分类决策树**：每个错误码/关键词对应什么处置策略（换号、冷却、透传、不罚号）。

### 2.3 行为层：最难

行为层回答"客户端为什么这么做、有什么隐含约束"。这部分需要**二进制分析 + 实测**结合：

- 为什么两个 token 刷新请求不能并发？
- 为什么 `X-Refresh-Token` 这个头不能在普通请求里带？
- 为什么某个字段的 `expiresIn` 超过 10 年要按脏数据处理？

这些答案都在客户端的**行为逻辑**里，不在任何文档里。

## 3. 为什么行为层最难

因为行为层往往是对**用户看不见的约束**的反应：

- **上游风控的暗规则**：某个头带了会触发风控，某个 UA 写死会导致服务端归因错乱
- **并发陷阱**：两个刷新同时发出，后写覆盖先写，服务端还不做 rotation 撤销
- **不可信字段**：服务端返回的 `expiresIn` 可能恒为 60 天，但 JWT 内部的时间戳才是真的

这些约束**没有一个写在文档里**，全部要靠实测撞出来，或者从二进制里读出来。

## 4. 三层模型对"做网关"的含义

理解三层模型，才能理解一个逆向反代项目的**技术分层**：

```
协议层 → 请求改写层（把客户端请求翻译成上游私有格式）
语义层 → 错误分类层（把上游错误翻译成客户端可理解的处置）
行为层 → 账号治理层（token 管理、指纹、冷却、池化）
```

其中：

- **协议层的改写**是"能转发"的门槛——12 步 JSON 改写这种
- **语义层的分类**是"会处理错误"的门槛——错误分类决策树
- **行为层的治理**是"能长期运营"的门槛——账号池、冷却、指纹、token 管理

如果你不知道某个错误码代表工具调用配对断裂、不知道某个模型对 `max_tokens` 有下限、不知道 429 里那句"将在某时刻重置"要按特定时区解释——那你的网关就是个"能转发、不会处理错误"的裸奔网关，账号该封还是封。

## 5. 一句话总结

> **协议是公开的，行为模型不是。**

你可以给任何 OpenAI 兼容的上游写一个 HTTP 代理。但真正区分"能转发的代理"和"能长期运营的网关"的，是语义层和行为层的深度。
